## 0. 문서 사용 규칙

1. 요구사항은 `docs/PRD.md`가 단일 출처다. 이 문서는 그 요구사항을 **어떻게 구성해 만족시키는지**만 정한다. PRD의 ID(`F05-R03`, `DI-02` 등)를 그대로 인용한다.
2. 이 문서에서 새로 정한 기술 선택에는 `AD-nn` ID를 붙였다. 2026-11-14에 개발자가 권장안을 모두 승인했고 `DECISIONS.md`에 기록했다(§20).
3. 라이브러리 버전은 적지 않는다. 착수 시점의 최신 안정 버전을 쓰고 `package.json`과 잠금 파일로 고정한다.
4. 외부 서비스의 리전, 요금, 무료 구간은 이 문서 작성 시점에 확인하지 않았다. 계정을 만들 때 공식 자료로 확인한다.
5. (초기값)으로 표시한 수치는 설정값 한 곳에 둔다.

## 5. 백엔드 구조

### 5.1 모듈

모듈형 단일 애플리케이션이다. 모듈은 기능 단위이며 PRD의 기능 ID와 대응한다.

| 모듈 | 책임 | PRD |
|---|---|---|
| `auth` | 인증 토큰 검증, 계정 생성·삭제 | F01 |
| `profile` | 러닝 프로필, 목표, 온보딩 진행 상태 | F02 |
| `plan` | 계획 생성·조회, 훈련 조회. Training Engine 호출 | F03, F06 |
| `workout` | 운동 기록, 훈련 연결 | F07 |
| `proposal` | 변경 제안 생성·승인·취소. **계획을 바꾸는 유일한 경로** | F05, `DI-01` |
| `chat` | 메시지 처리, AI Orchestrator, 도구 레지스트리, LLM 게이트웨이 | F04 |
| `usage` | 이용량 집계와 한도 판정 | F10, §8 |
| `subscription` | 구독 상태, 구독 서비스 웹훅 | F10 |
| `summary` | 주간 요약 수치, 주간 AI 피드백 | F08 |
| `notification` | 알림 설정, 푸시 토큰, 발송 | F09 |
| `jobs` | 내부 작업 엔드포인트 | F08, F09 |
| `analytics` | 분석 이벤트 전송 | F11 |

### 5.2 모듈 간 규칙

1. 다른 모듈의 테이블에 직접 쓰지 않는다. 그 모듈의 서비스를 호출한다.
2. 훈련 계획의 훈련(PlannedSession)을 수정하는 코드는 `proposal` 모듈의 승인 처리에만 있다. 최초 계획 저장만 `plan` 모듈이 한다.
3. LLM을 호출하는 코드는 `chat` 모듈의 LLM 게이트웨이에만 있다. `summary` 모듈도 이 게이트웨이를 쓴다.
4. 외부 서비스 호출은 트랜잭션 밖에서 한다. 분석 이벤트와 푸시는 커밋 후에 보내고, 실패해도 본 처리를 실패시키지 않는다.

### 5.3 공통 처리

| 항목 | 방식 |
|---|---|
| API 형식 | REST + JSON, 경로 접두어 `/v1` |
| 인증 | 전역 가드가 모든 요청의 토큰을 검증한다. 예외는 웹훅, 내부 작업, 상태 확인뿐이며 각각 별도 비밀값으로 보호한다. |
| 사용자 식별 | 검증된 토큰에서 얻은 사용자 ID만 쓴다. 요청 본문·경로의 사용자 ID는 받지 않는다(`DI-07`). |
| 입력 검증 | `packages/shared`의 zod 스키마로 모든 요청을 검증한다. |
| 오류 응답 | `{ code, message }` 형식. `code`는 앱이 분기하는 고정 문자열, `message`는 사용자에게 보여 줄 한국어 문장이다. 내부 오류 내용은 넣지 않는다. |
| 요청 제한 | 사용자별 분당 요청 수 제한. 프로세스 메모리 기반이다(§18). |
| 앱 버전 확인 | 앱이 모든 요청에 앱 버전을 보낸다. 서버가 지원하지 않는 버전이면 업데이트 안내 오류를 돌려주고 앱은 업데이트 화면을 띄운다. 출시 후에는 넣을 수 없는 장치라 첫 버전부터 포함한다. |
| 로그 | 구조화된 로그를 표준 출력으로 낸다. 채팅 본문, 메모, 토큰은 로그에 남기지 않는다. |

## 6. Training Engine

`packages/training-engine`은 세 함수 묶음을 내보낸다. 세부 규칙은 PRD §7을 따른다.

| 구성 | 입력 | 출력 |
|---|---|---|
| 생성기 | 프로필, 목표, 오늘 날짜 | 훈련 목록, 경고 |
| 변경기 | 현재 계획 상태(훈련, 완료 여부), 변경 요청, 오늘 날짜 | 변경안(이동·생략·완화 목록, 영향 요약) 또는 불가 사유 |
| 검증기 | 계획 상태, 오늘 날짜. 일정 변경의 변경안이면 변경 전 계획 상태와 변경 사유 | 통과 또는 위반 규칙 ID 목록 |

설계 규칙:

1. **오늘 날짜는 인자로 받는다.** 시스템 시각을 읽지 않는다. 같은 입력이면 같은 결과가 나온다(`TE-R09`).
2. **검증기는 생성기·변경기의 내부 함수를 쓰지 않는다.** 독립적으로 규칙을 검사한다(PRD §7.1). 입력의 주차(`weekNumber`)도 믿지 않고 날짜로 주를 계산한다.
3. **API가 저장 전에 검증기를 다시 호출한다.** 생성기·변경기가 검증기를 통과한 결과만 내도록 만들더라도, 저장 직전 검사는 API의 책임이다(`TE-S12`).
4. **안전 수치는 한 파일의 상수로 둔다**(`D-04`에서 확정).
5. 기준 계획표는 이 패키지 안의 데이터 파일로 둔다.
6. 날짜는 `YYYY-MM-DD` 문자열로 주고받는다(§13).

## 7. AI 오케스트레이션

요구사항은 PRD §6이다. 여기서는 서버 내부 구성을 정한다.

### 7.1 구성

| 구성 | 책임 |
|---|---|
| 메시지 처리기 | 중복 확인, 한도 확인, 저장, 응답 조립 |
| 컨텍스트 구성기 | LLM에 보낼 내용 조립 |
| LLM 게이트웨이 | 공급자 API 호출. 공급자 SDK를 쓰는 유일한 곳 |
| 도구 레지스트리 | 도구 정의, 인자 검증, 실행 |
| 호출 기록기 | 토큰 수, 비용 추정치, 성공 여부 저장(`F11-R02`) |

### 7.2 LLM 게이트웨이

공급자에 묶이지 않는 인터페이스 하나를 둔다.

| 입력 | 출력 |
|---|---|
| 시스템 지침, 대화, 도구 정의, 최대 출력 토큰 | 텍스트, 도구 호출 목록, 종료 사유, 입력·출력 토큰 수 |

- 공급자를 바꿀 때 이 모듈만 고친다. 평가 세트(PRD §12)는 이 인터페이스를 통해 공급자별로 돌린다.
- 정상 종료가 아닌 응답(출력 한도 도달, 공급자의 응답 거부 등)은 실패로 처리하고 이용량을 차감하지 않는다(`F04-R10`).
- 일시적 오류는 1회 재시도한다(초기값). LLM 호출 1회 제한 시간은 30초, 메시지 1건 전체 처리 제한 시간은 60초다(초기값).
- 테스트에서는 이 인터페이스의 가짜 구현을 쓴다. 실제 LLM 없이 도구 흐름을 검증한다.

### 7.3 도구 레지스트리

도구 하나는 이름, 설명, 인자 스키마(zod), 실행 함수로 구성된다. 목록은 PRD §6.2의 7개다.

1. 인자 스키마에서 LLM에 보낼 도구 정의를 만든다. 정의를 손으로 따로 쓰지 않는다.
2. LLM이 보낸 인자는 공급자 쪽 스키마 강제 기능을 쓰더라도 서버가 다시 검증한다.
3. 레지스트리에 없는 도구 이름이나 검증에 실패한 인자는 실행하지 않고 오류를 LLM에 돌려준다.
4. 실행 함수는 인증된 사용자 ID를 서버에서 주입받는다. 도구 인자에는 사용자 ID가 없다.
5. 데이터를 바꾸는 실행 함수를 등록하지 않는다. 제안 도구는 `proposal` 모듈에 대기 상태 제안을 만드는 것까지만 한다.

### 7.4 컨텍스트 구성

보내는 순서를 고정한다. 앞부분이 요청마다 같아야 공급자의 프롬프트 캐시를 쓸 수 있다.

| 순서 | 내용 | 변동 |
|---|---|---|
| 1 | 도구 정의 | 고정 |
| 2 | 시스템 지침 (PRD §6.7의 `AI-01`~`AI-10`, `AI-12`) | 고정 |
| 3 | 코치 말투 지침 (PRD `AI-11`). `users.coach`에 맞는 것 하나 | 코치별 고정 |
| 4 | 오늘 날짜, 프로필 요약, 이번 주 계획 요약 | 사용자·날짜별 |
| 5 | 최근 대화 10개(초기값) | 요청별 |
| 6 | 새 사용자 메시지 | 요청별 |

- 시스템 지침은 저장소의 파일로 관리하고 버전을 붙인다. 호출 기록에 지침 버전을 남겨 평가 결과와 연결한다.
- 과거 대화의 카드는 짧은 텍스트 요약으로 바꿔 보낸다(예: "변경 제안 카드, 상태: 승인됨").
- 코치 말투 지침은 공통 지침 뒤에 둔다. 코치가 3명뿐이라 코치별로 캐시가 나뉘어도 공통 부분은 함께 쓴다. 말투 지침에는 안전·도구 규칙을 넣지 않고 공통 지침에만 둔다.
- 4번의 요약은 대화의 출발점일 뿐이다. 계획·기록에 대해 답할 때는 조회 도구를 호출한다(`AI-01`).

### 7.5 메시지 처리 순서

앱은 메시지 전송 요청 하나를 보내고 완성된 응답을 받는다.

1. `(사용자, 클라이언트 메시지 ID)` 유일 제약으로 사용자 메시지를 "처리 중" 상태로 저장한다. 이미 있으면 새로 처리하지 않고 기존 상태(처리 중 / 완료된 응답 / 실패)를 돌려준다.
2. 같은 사용자의 "처리 중" 메시지가 있으면 거부한다. 2분(초기값) 넘게 처리 중인 메시지는 실패로 본다.
3. 이용 한도를 확인한다. 초과면 LLM을 호출하지 않고 한도 안내 카드를 저장·반환한다.
4. 컨텍스트를 구성하고 LLM을 호출한다. 도구 호출이 있으면 실행하고 결과를 붙여 다시 호출한다. 최대 5회(초기값).
5. 성공하면 AI 메시지와 카드 참조를 저장하고, 사용자 메시지를 완료로 바꾸고, 이용량을 1 올린다. 이 셋은 한 트랜잭션이다.
6. 실패하면 사용자 메시지를 실패로 바꾼다. 이용량은 올리지 않는다. 이미 만들어진 대기 제안은 취소 처리한다.
7. 성공·실패와 관계없이 LLM 호출마다 호출 기록을 남긴다.

요청이 중간에 끊기면 앱은 같은 클라이언트 메시지 ID로 다시 보낸다. 1번 규칙에 따라 중복 처리되지 않고 결과만 받는다.

사용자당 동시에 처리되는 메시지가 1건이므로, 채팅 이용량은 "확인 후 처리, 성공 시 증가" 순서로도 한도를 넘지 않는다(`DI-12`).

### 7.6 승인 처리

`proposal` 모듈의 승인은 단일 DB 트랜잭션이다(`DI-02`). 잠금 순서는 항상 제안 → 계획이다.

1. 제안 행을 잠그고 읽는다. 다른 사용자의 제안이면 거부한다.
2. 이미 승인된 제안이면 저장된 결과를 그대로 돌려주고 끝낸다(`DI-04`).
3. 취소·만료·대체된 제안이면 거부한다. 만료는 만료 시각과 현재 시각을 비교해 판정한다. 만료 처리용 예약 작업은 두지 않는다.
4. 계획 행을 잠그고 버전을 제안의 기준 버전과 비교한다. 다르면 거부한다(`DI-03`).
5. 대상 훈련이 여전히 미완료이고 오늘 이후인지 확인한다.
6. 변경을 적용한 결과를 Training Engine 검증기로 검사한다.
7. 이용량이 차감되는 제안이면 "현재 값이 한도 미만일 때만 1 증가"하는 조건부 갱신을 한다. 갱신된 행이 없으면 전체를 되돌리고 한도 안내를 돌려준다.
8. 훈련 수정, 변경 이력 추가, 계획 버전 증가, 제안 상태 변경, 결과 시스템 메시지 추가를 수행하고 커밋한다.
9. 커밋 후 분석 이벤트를 보낸다.

운동 기록의 저장·삭제는 계획 버전을 올리지 않지만 같은 계획 행 잠금을 잡는다. 승인과 기록 저장이 동시에 일어나도 5번 검사가 올바른 상태를 본다.

## 9. 인증

`AD-05` 기준이다.

1. 앱이 네이티브 카카오 / Apple / Google 로그인으로 ID 토큰을 받는다. 카카오 로그인은 카카오 SDK의 OpenID Connect ID 토큰을 쓴다. 카카오 SDK를 앱에 넣는 방법(네이티브 모듈 의존성)은 `T-106`에서 이유와 함께 제안한다.
2. 앱이 ID 토큰을 인증 서비스에 넘겨 세션(액세스 토큰, 갱신 토큰)을 받는다. 토큰 갱신은 인증 서비스의 앱 SDK가 처리한다.
3. 앱은 API 요청마다 액세스 토큰을 보낸다.
4. API는 인증 서비스의 공개 키로 토큰 서명을 검증하고 사용자 ID를 얻는다. 요청마다 인증 서비스를 호출하지 않는다.
5. 첫 요청 시 API가 자기 DB에 User 행을 만든다. 기본 키는 인증 서비스의 사용자 ID다.

계정 삭제(`F01-R05`, `DI-11`): API가 자기 DB의 개인 데이터를 삭제한 뒤 인증 서비스의 사용자를 삭제한다. Apple 로그인 사용자는 Apple 쪽 토큰 폐기도 요청한다. 구독 서비스의 사용자 정보도 삭제를 요청한다. 중간에 실패하면 삭제 미완료 상태를 남기고 다시 시도할 수 있게 한다. 체험분을 다시 받지 못하게 하는 식별 해시와 사용 횟수(`usage_trials`)만 남긴다(`DATABASE.md` §7).

API는 인증 서비스를 로그인 수단으로만 쓴다. 앱이 인증 서비스를 통해 DB에 직접 접근하는 기능은 쓰지 않는다.

## 10. 구독

`AD-08` 기준이다.

```text
앱 ──(구매)──► 구독 서비스 SDK ──► 스토어
                    │
구독 서비스 ──(웹훅)──► API ──► Subscription 테이블
앱 ──(구매 직후 확인 요청)──► API ──(조회)──► 구독 서비스
```

1. 구독 서비스의 사용자 식별자로 우리 사용자 ID를 쓴다.
2. **권한 판정은 API의 Subscription 테이블만 본다**(`F10-R03`). 앱 SDK가 알려 주는 구독 상태는 화면 표시에만 쓴다.
3. 웹훅은 비밀값을 검증하고, 이벤트 ID 유일 제약으로 중복 수신을 무시한다.
4. 구매 직후에는 웹훅이 늦을 수 있다. 앱이 확인을 요청하면 API가 구독 서비스에 직접 조회해 테이블을 갱신한다(`F10-R09`). 구독 복원도 같은 경로다.
5. 한도 판정은 `usage` 모듈이 Subscription 상태와 UsageCounter, UsageTrial(무료의 가입 체험분)을 읽어서 한다. 무료는 체험분에서 먼저 차감한다(PRD §8.2).

## 11. 알림과 예약 작업

`AD-09`, `AD-11` 기준이다.

예약 작업은 API의 내부 작업 엔드포인트로 구현하고, 호스팅 플랫폼의 예약 실행기가 정해진 시각에 호출한다. 엔드포인트는 비밀값으로 보호한다. API 프로세스 안에서 타이머를 돌리지 않으므로 인스턴스 수나 재시작에 영향을 받지 않는다.

| 작업 | 실행 시각 (`Asia/Seoul`, 초기값) | 내용 |
|---|---|---|
| 예정 운동 알림 | 매시 정각, 08시~20시 | 오늘 훈련이 있고 알림 시각이 지금인 사용자에게 발송. 같은 작업이 같은 조건(알림 시각이 지금, 예정 운동 알림 켬)으로 대회 전날 알림(내일이 대회 날)과 계획 종료 알림(어제가 계획의 마지막 날)도 보낸다(`F09-R08`, `F09-R09`) |
| 미완료 훈련 안내 | 매일 09시 | 어제 훈련이 미완료인 사용자에게 하루 한 번 발송. 이틀 전 훈련으로는 보내지 않는다(PRD `F09-R11`) |
| 주간 요약 | 일요일 20시 | 주간 수치 계산·저장, Pro는 AI 피드백 생성, 요약 알림 발송. 계획한 훈련도 기록도 없는 주에는 알림을 보내지 않는다(`F09-R10`) |

1. **중복 발송은 DB가 막는다.** 발송 기록에 `(사용자, 알림 종류, 날짜)` 유일 제약을 두고, 기록 추가에 성공한 경우에만 발송한다. 작업이 두 번 실행되어도 한 번만 간다. 발송 기록은 PRD §9에 없는 엔티티이며 `DATABASE.md`에 추가한다.
2. 예정 운동 알림 시각은 정시 단위로만 고를 수 있게 한다. 작업 실행 주기를 1시간으로 유지하기 위해서다.
3. 작업 실행 시각 자체가 오전 8시~오후 9시 안에 있으므로 야간 발송 금지(`F09-R06`)가 지켜진다.
4. 알림 문구는 템플릿이다. LLM을 호출하는 것은 주간 요약의 Pro 피드백뿐이다.
5. 발송 서비스가 "유효하지 않은 토큰"으로 응답하면 그 토큰을 지운다.
6. 주간 요약 작업은 사용자를 순서대로 처리하고, 한 사용자의 실패가 다른 사용자를 막지 않는다. 주간 요약에 `(사용자, 주)` 유일 제약이 있어 다시 실행해도 중복 생성되지 않는다(`F08-R02`).

제안 만료와 계획 종료는 조회 시점에 날짜를 비교해 판정한다. 예약 작업이 필요 없다.

## 12. 분석과 관측

| 항목 | 방식 |
|---|---|
| 분석 이벤트 | **서버가 아는 이벤트는 서버에서 보낸다.** `F11-R01`의 이벤트 중 `paywall_viewed`와 앱 실행(재방문 측정용)만 앱에서 보낸다. 이벤트 누락이 줄고, 전송 코드가 `analytics` 모듈 한 곳에 모인다. |
| 이벤트 내용 | 사용자 ID와 이벤트 속성만 담는다. 채팅 본문, 메모는 넣지 않는다(`F11-R04`). |
| AI 비용 | DB의 호출 기록(AiCallLog)이 원본이다. 사용자별 월 비용은 SQL로 집계한다(`AC-F11-02`). |
| 오류 | 앱과 API 모두 오류 모니터링 서비스로 보낸다. |
| 상태 확인 | API에 DB 연결을 확인하는 상태 확인 엔드포인트를 둔다. |
| 운영 조회 | 관리자 화면을 만들지 않는다. DB 호스팅의 콘솔에서 조회한다(§18). |

광고 플랫폼(미정)에 따라 설치 측정용 SDK가 추가로 필요할 수 있다. 광고 플랫폼을 정할 때 확인한다.

## 13. 날짜와 시간

| 대상 | 저장 형식 | 규칙 |
|---|---|---|
| 훈련 날짜, 운동 날짜, 대회 날짜 | 날짜 (`YYYY-MM-DD`) | 시각과 시간대를 붙이지 않는다(`DI-09`). |
| 생성 시각, 만료 시각 등 | UTC 시각 | 표시할 때만 `Asia/Seoul`로 바꾼다. |

1. "오늘"은 서버가 `Asia/Seoul` 기준으로 계산한다. 이 계산은 함수 하나에만 있다. 앱이 보낸 날짜를 "오늘"로 믿지 않는다.
2. 서버와 Training Engine 사이, API와 앱 사이에서 날짜는 문자열로 주고받는다. 시간대가 있는 날짜 객체로 바꾸지 않는다.
3. 월 초기화(`D-08`)는 `Asia/Seoul` 기준 연·월을 UsageCounter의 키로 써서 구현한다. 초기화 작업이 필요 없다.
4. 주는 월요일에 시작한다(PRD §1.5).

| 입력 | 모든 요청을 스키마로 검증한다. 채팅 메시지 길이 제한(`F04-R09`). 채팅은 글자만 받는다. |
| 비밀값 | 호스팅 플랫폼의 비밀값 저장소에 둔다. 저장소와 앱 번들에 넣지 않는다. |
| 웹훅 · 내부 작업 | 각각 별도의 비밀값으로 검증한다. |
| LLM | 도구 인자 재검증, 도구 호출 반복 제한, 실행 권한 없음(§7.3). 사용자 입력과 도구 결과 안의 지시문은 데이터로 취급한다(`AI-07`). |
| 남용 방지 | 사용자별 요청 제한, 월 이용 한도, 메시지 길이·출력 토큰 제한 |
| 개인정보 | 로그와 분석 이벤트에 채팅 본문·메모를 남기지 않는다. 오류 모니터링에 요청 본문을 보내지 않는다. |
| DB 접근 | API만 접속한다. 앱은 DB 접속 정보를 갖지 않는다. |

## 15. 환경, 배포, CI

| 항목 | 방식 |
|---|---|
| 환경 | 로컬과 운영 두 가지(`AD-14`). 결제는 스토어 테스트 환경, 앱은 내부 테스트 배포(TestFlight, 내부 테스트 트랙)로 검증한다. |

| CI | 푸시마다 타입 검사, 린트, 테스트를 돌린다. |
| 백업 | DB 호스팅의 자동 백업을 쓴다. 선택한 요금제의 백업 주기와 보존 기간을 확인한다. |

## 16. 외부 서비스와 개인정보 흐름

개인정보 처리방침과 `D-12` 법률 검토의 입력 자료다. 어떤 서비스에 무엇이 전달되는지 정리한다.

| 서비스 | 전달되는 정보 | 목적 |
|---|---|---|
| 인증 서비스 | 로그인 제공자 식별자, 이메일(제공되는 경우) | 로그인 |
| DB 호스팅 | 모든 서비스 데이터 | 저장 |
| API 호스팅 | 처리 중인 모든 요청 데이터 | 처리 |
| LLM 공급자 | 채팅 내용, 프로필 요약, 훈련 계획, 운동 기록 요약 | AI 응답 생성 |
| 구독 서비스 | 사용자 ID, 구매 내역 | 구독 검증 |
| 푸시 발송 서비스 | 푸시 토큰, 알림 문구 | 알림 |
| 분석 서비스 | 사용자 ID, 이벤트 속성 | 사용 분석 |
| 오류 모니터링 | 사용자 ID, 오류 정보 | 오류 추적 |

1. LLM에는 사용자를 식별하는 이름·이메일을 보내지 않는다.
2. 서버를 국내 리전에 두더라도 LLM, 분석, 오류 모니터링, 구독 서비스는 해외 사업자일 가능성이 높다. 국외 이전 고지 대상은 `D-12`에서 확인한다.
3. LLM 공급자를 고를 때(`D-03`) 입력 데이터의 보존 기간과 학습 사용 여부를 확인 항목에 넣는다.

## 17. 테스트 구조

요구사항은 PRD §12다.

| 대상 | 방식 |
|---|---|
| `training-engine` | 단위 테스트 + 불변식 테스트(fast-check로 입력을 자동 생성해 모든 결과가 검증기를 통과하는지 확인). DB 없이 실행된다. |

| AI 도구 흐름 | LLM 게이트웨이의 가짜 구현으로 도구 호출 → 제안 생성 → 카드 반환을 검증한다. |

| `apps/mobile` | 화면 로직 단위 테스트는 최소한으로 하고, 주요 흐름은 실기기 점검으로 확인한다. |

## 18. 규모 가정과 확장 시점

출시 후 30일의 목표 가입자는 50명이다. 아래는 그 규모에 맞춰 의도적으로 단순하게 둔 부분과, 바꿔야 하는 시점이다.

| 단순화 | 한계 | 바꿀 시점 |
|---|---|---|
| API 인스턴스 1~2개, 요청 제한은 프로세스 메모리 기반 | 인스턴스가 늘면 제한이 인스턴스별로 따로 적용된다 | 인스턴스를 3개 이상으로 늘릴 때 공유 저장소 기반으로 교체 |
| 채팅 요청이 LLM 응답까지 연결을 유지 | 동시 대화가 많으면 연결 수가 늘고, 응답이 길어지면 체감 대기가 커진다 | 평균 응답 시간이 10초를 넘거나 사용자 불만이 있을 때 스트리밍 도입(`D-13` 재검토) |
| 주간 요약 작업이 사용자를 순서대로 처리 | Pro 사용자가 많으면 작업 시간이 길어진다 | 작업 1회가 10분을 넘을 때 작업 큐 도입 |
| 관리자 화면 없음 | 문의 대응 시 DB 콘솔에서 직접 조회 | 문의 대응이 주 단위로 반복될 때 |
| 환경이 로컬·운영 둘뿐 | 운영 DB에 적용하기 전 마이그레이션을 실제 데이터로 검증할 수 없다 | 유료 사용자가 생긴 뒤 스테이징 추가 |
| LLM 공급자 1곳 | 공급자 장애 시 채팅 중단. 캘린더·기록은 계속 동작한다 | 장애가 사업에 영향을 줄 만큼 반복될 때 |

## 20. 기술 선택과 대안

2026-11-14에 아래 권장안이 모두 승인되었다. `D-11`(분석·오류 모니터링·호스팅)과 `D-05`(구독 서비스)의 구체적인 선택을 포함한다. 대안은 결정 배경으로 남겨 둔다.

### AD-05. 인증 — Supabase Auth

| 대안 | 장점 | 단점 |
|---|---|---|
| **Supabase Auth (선택)** | 세션 발급·갱신·폐기를 직접 만들지 않는다. Apple / Google / 카카오 로그인 지원(카카오의 ID 토큰 로그인 지원 여부는 `T-106`에서 확인한다). DB 호스팅과 같은 서비스라 계정이 하나 줄어든다. | 외부 의존. 사용자 계정이 인증 서비스와 우리 DB 두 곳에 존재한다. |
| 직접 구현 (ID 토큰 검증 + 자체 세션) | 외부 의존 없음, 구조 단순 | 갱신 토큰 회전·폐기 등 보안에 민감한 코드를 직접 작성하고 유지한다. |
| Firebase Auth | 성숙한 서비스 | 앱에 네이티브 SDK가 추가되고, DB 호스팅과 사업자가 달라진다. |

### AD-06 / AD-07. 호스팅 — Supabase(DB) + Google Cloud Run(API), 서울 리전

선택 기준 1순위는 **DB와 API를 같은 지역, 가능하면 서울 리전에 두는 것**이다. 서로 가까워야 트랜잭션이 빠르고, 국내 저장은 `D-12`의 국외 이전 고지 범위를 줄인다.

| 대안 | 장점 | 단점 |
|---|---|---|
| **Supabase + Cloud Run (선택)** | 두 서비스 모두 서울 리전을 제공하는 것으로 알고 있다(확인 필요). 관리형 PostgreSQL과 자동 백업, 컨테이너 배포, 예약 실행기(Cloud Scheduler) 제공. | 계정이 두 개다. Cloud Run은 초기 설정(프로젝트, 권한, 이미지 저장소)이 PaaS보다 많다. |
| Supabase + Git 연동 PaaS (Railway, Render, Fly.io 등) | 배포 설정이 가장 간단하다. | 서울 리전이 없을 수 있다(확인 필요). DB와 지역이 달라지면 요청마다 지연이 더해진다. |
| AWS 단일 구성 (RDS + 컨테이너 서비스, 서울) | 한 사업자, 서울 리전 | 설정과 운영 부담이 가장 크다. |

확인할 것: 두 서비스의 서울 리전 제공 여부, 상시 인스턴스 1개의 월 비용, 선택한 DB 요금제의 백업 정책, 무료 요금제의 휴면 정책.

| ID | 선택 | 선택 이유 | 대안 |
