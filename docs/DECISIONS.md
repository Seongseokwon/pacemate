## 2026-11-14 — API 명세 v1.0 승인

개발자가 `docs/API_SPEC.md`와 그 §8을 승인했다.

- 운동 기록의 컨디션·운동 강도는 선택 입력이다. 필수는 날짜·거리·시간이다.
- 활성 계획이 있으면 프로필을 직접 수정할 수 없고, 목표·프로필 변경 제안을 거친다.
- 채팅 재전송은 같은 `clientMessageId`로 다시 보내는 방식이다.
- 기록 중복·페이스 확인은 서버 오류 응답 후 앱이 확인 필드를 붙여 다시 보내는 방식이다.
- 홈 화면 전용 엔드포인트(`GET /v1/home`)를 둔다.

## 2026-11-14 — 자체 디자인 시스템 (UX-00)

Astryx 디자인 시스템(https://astryx.atmeta.com/)의 적용을 검토했다. 웹 전용이라 React Native + Expo(`D-01`)에서 컴포넌트를 쓸 수 없고, 토큰 값만 뽑아 쓰는 방식은 가능했으나 이점이 작았다.

개발자가 **자체 디자인 시스템**으로 결정했다. 토큰과 컴포넌트를 `docs/UI_UX.md`가 정의하고 `apps/mobile/src/ui/`에 직접 구현한다. Astryx의 토큰·테마·패키지를 쓰지 않는다.

`UX-01`~`UX-06`(강조색, 글꼴, 다크 모드, 아이콘, 캘린더, 하단 시트)은 승인 대기다.

## 2026-11-14 — 테스트 도구와 모듈 형식 변경 (AD-12)

`T-103`에서 NestJS 최신 버전(12)의 기본 구성이 ESM + Vitest임을 확인했다. AD-12(Jest 하나로 통일)의 근거였던 "NestJS와 Expo 모두 Jest가 기본"이 더 이상 맞지 않는다.

개발자가 **NestJS 12의 기본 구성을 따르기로** 결정했다.

- `services/api`, `packages/shared`, `packages/training-engine`: ESM, Vitest
- `apps/mobile`: Expo 기본인 Jest
- 불변식 테스트의 fast-check는 그대로다.

함께 정한 것: 패키지는 `dist`로 빌드해 쓰고(`pnpm build`), 린트는 저장소 공통 ESLint를 유지한다(NestJS 기본인 oxlint를 쓰지 않는다).

## 2026-11-14 — 훈련 안전 규칙의 구조 변경 (D-04 일부)

`T-201` 초안(`docs/T-201-TRAINING-DRAFT.md`)을 교차 검토하면서, 기존 규칙으로는 회복 주를 지날 때마다 훈련량이 줄어 대회 준비 계획을 만들 수 없음을 확인했다. 개발자가 아래 여섯 가지를 승인했고 PRD §7에 반영했다.

| # | 결정 | PRD |
|---|---|---|
| 1 | 주간 증가 한도의 기준을 직전 주에서 최근 4주의 고점으로 바꾼다. 회복 주 다음 주는 고점까지만 복귀한다 | `TE-S01` |
| 2 | 계획을 만들 수 있는지는 대회 전에 도달할 수 있는 최장 달리기 거리로 판정한다. 도달할 수 없으면 완주 준비 계획을 만들지 않고 기초 훈련 계획만 제시한다. 둘 다 가능하면 사용자가 고른다 | `TE-G06`, `F03-R05`, `F03-R06` |
| 3 | 사용자는 목표 기록 값을 유지할 수 있다. 그 선택은 계획의 훈련량과 강도를 올리지 않는다 | `TE-G06` |
| 4 | 최근 주간 거리가 0이거나 없으면 시간 기반 걷고 달리기 계획으로 시작한다. 첫 주는 "쉬지 않고 달릴 수 있는 시간"을 기준으로 한다 | `TE-S06`, `TE-G05`, `TE-S14` |
| 5 | 한 번의 달리기 거리가 최근 30일 최장 거리의 110%를 넘지 않는 규칙을 추가한다 | `TE-S13` |
| 6 | 대회 당일의 거리는 훈련량 계산에서 뺀다 | `TE-S08` |

확정한 것은 규칙의 구조다. 수치(110%, 30일, 4주)는 초기값이고, 목표별 도달 기준 거리, 시간 기반 주의 구성, 입문 계획, 주 2회·4~5회 구성은 정해지지 않았다. 러닝 훈련 전문가의 검토 전에는 D-04를 확정으로 바꾸지 않는다.

함께 바뀐 문서: `API_SPEC.md` §3.3(계획 종류와 미리보기의 선택지), `DATABASE.md` §3.3(`training_plans.kind`), `UI_UX.md` §6.2(계획 종류 선택).

`T-202`의 초안을 교차 검토하면서 PRD §7.4만으로는 판정할 수 없는 부분을 확인했고, 개발자가 아래와 같이 승인했다. `D-04`는 여전히 확정이 아니며 수치는 모두 초기값이다.

| 항목 | 결정 | PRD |
|---|---|---|
| 주의 계산 | 주는 월요일부터 일요일까지다. 검증기는 날짜로 주를 직접 계산하고 입력의 주차를 믿지 않는다 | §1.5, §7.4 |
| 변경안의 검증 입력 | 일정 변경의 변경안을 검증할 때는 변경 전 계획과 변경 사유를 함께 넘긴다(`ValidateInput.change`). 변경 전후의 훈련과 주간 총량을 함께 비교한다. 놓친 훈련을 다른 훈련의 거리 증가로 보충하지 않는다 | `TE-S09` |
| 통증·피로 | 피로 변경은 훈련량·강도를 높이지 않는다. 통증은 휴식 선택지를 먼저 안내한다 | `TE-S11` |
| 회복 주 | 초기값은 4주마다 25% 감량이다. 줄이는 기준은 직전 주가 아니라 최근 4주 고점이다(`TE-S01`과 같은 기준) | `TE-S02` |
| 회복 주의 판정 | 주간 거리가 최근 4주 고점보다 20% 이상 적은 주를 회복 주로 본다. 더 많이 줄인 주도 회복 주다. 회복 주 없이 4주째가 되는 주부터는 고점을 넘지 못한다. 고점을 넘지 않는 유지 주간과 시간 기반 주에는 회복 주를 요구하지 않는다 | `TE-S02`, `TE-S01` |
| 대회 전 감량 | 대회가 있는 주의 훈련 거리(대회 당일 제외)는 최근 4주 고점보다 25% 이상 적어야 한다. 대회가 없는 계획에는 적용하지 않는다 | `TE-S08` |
| 대회 일정의 강도 | "높음"으로 본다. 대회 전날과 다음 날에 `tempo`와 `long`을 두지 않는다 | `TE-S04` |
| 달리기 구간 길이 | 훈련에 걷고 달리기에서 한 번에 달리는 시간(분)을 더한다(`EngineSession.runIntervalMin`, `planned_sessions.run_interval_min`). 첫 주에는 이 값이 "쉬지 않고 달릴 수 있는 시간" 범주의 하한을 넘지 않는다: 10~30분은 10분, 30~60분은 30분, 60분 이상은 60분. 하한이 없는 10분 미만은 1분으로 둔다(Claude Code가 제안한 초기값) | `TE-S14` |
| "첫 주" | 생략하지 않은 훈련이 처음 있는 주다. 계획의 첫 주 훈련을 모두 생략해도 다음 주가 "비교할 달리기가 없다"는 이유로 계속 거절되지 않게 한다 | `TE-S06`, `TE-S13`, `TE-S14` |
| `tempo`의 주 3회 | 그 주에 배치된, 생략하지 않은 훈련의 수로 센다. 훈련을 생략해 주 3회에 못 미치면 변경기가 `tempo`도 함께 바꿔야 한다 | `TE-S07` |
| 지난 주 | 이미 지난 주의 위반만으로 이후의 변경을 막지 않는다. 지난 주의 훈련은 최근 4주 고점, 최근 30일 최장 거리, 연속된 고강도 배치의 기준으로만 쓴다 | §7.4 |
| 기록이 없는 14일 | 운동을 하지 않았다고 단정하지 않고 확인을 요청한 뒤 재계산을 제안한다. 계획의 통과·위반이 아니므로 검증기의 규칙 ID(`SafetyRuleId`)에서 뺀다. 요구사항 ID `TE-S10`은 그대로 둔다 | `TE-S10` |
| 형식이 맞지 않는 훈련 | 걷고 달리기가 아닌데 거리가 없거나, 거리와 시간이 모두 없는 훈련은 `TE-S14` 위반으로 보고한다 | `TE-S14` |
| 시간 기반 → 거리 기반 전환 | 방향만 정했다: 최근 실제 기록과 수기 입력을 활용하고, 걷기를 포함한 거리와 달린 거리를 구분하며, 기록이 부족하면 시간 기반을 유지한다. 사용자가 부담을 느끼면 더 짧은 거리나 시간 기반 계획을 제시한다. 1회 3km는 시작 참고값이고 더 낮출 수 있다. 전환 조건과 상한은 `T-201`에서 정하며, 그 전에는 검증기가 전환하는 주를 통과시키지 않는다 | `TE-S14` |

아직 정하지 않은 것:

- 시간 기반과 거리 기반 사이의 전환 조건과 상한(`T-201`). 정해지기 전에는 검증기가 전환하는 주를 통과시키지 않는다. 시간 기반 주는 거리가 0이라 거리 기반으로 넘어가는 주가 `TE-S01`과 `TE-S13`에, 거리 기반에서 시간 기반으로 돌아가는 주가 `TE-S14`에 걸린다.
- 목표 변경으로 다시 계산한 계획의 검증 입력(`T-401`). 2026-11-14부터 미정이다.
- 훈련을 생략하면 그 주의 거리가 줄어 다음 주의 상한(`TE-S01`)이 낮아지고, 길게 달리기의 비율(`TE-S03`)이 올라간다. 변경기가 같은 주의 다른 훈련과 다음 주를 함께 줄일지, 기준값 계산에는 생략한 훈련을 넣을지를 `T-401`에서 정한다(`TE-R08`).
- 대회가 월요일이나 화요일이면 대회가 있는 주에 훈련이 거의 없어 `TE-S08`이 직전 주를 줄이게 하지 못한다. 기준을 "대회 전 7일"로 바꿀지는 `T-201`에서 정한다.

함께 바뀐 문서: `PRD.md` §7.2, §7.4, `ARCHITECTURE.md` §6, `DATABASE.md` §3.4, `DEVELOPMENT_PLAN.md`(`T-202`, `T-204`). 코드: `packages/training-engine`의 `ValidateInput`, `SafetyRuleId`, `EngineSession`.

## 2026-11-16 — 생성기의 초기값 (T-201, D-04 일부)

개발자가 `T-201`을 Codex에서 Claude Code로 넘겼고, Claude Code가 아래 초기값을 제안했다. **이 기록은 PR을 병합한 때부터 유효하다**(위 "Training Engine을 초기값으로 먼저 개발한다"의 절차). `D-04`는 여전히 확정이 아니며, 값은 안전성이 검증된 처방이 아니다. 근거, 대안, 확인 방법은 `docs/T-201-TRAINING-DRAFT.md` §10에 있다.

계획표의 형태: 목표 × 수준별 표 9개를 두지 않고, 증가 규칙 하나 + 횟수별 구성 + 목표별 도달 조건으로 나눈다.

| 항목 | 초기값 | PRD |
|---|---|---|
| 수준 분류 | 세 항목 중 가장 낮은 수준. 달릴 수 있는 시간: 30분 미만 입문, 30~60분 초급, 60분 이상 중급. 최근 주간 거리: 없음·10km 미만 입문, 25km 미만 초급, 25km 이상 중급. 경험: 처음 입문, 6개월 미만 초급, 그 이상 중급 | `TE-G01` |
| 거리 기반으로 시작하는 기준 | 최근 주간 거리 6km 이상. 그보다 적으면 0km·없음과 같이 시간 기반으로 시작한다 | `TE-G05`, `TE-S06` |
| 주간 거리의 진행 | 4주 주기. 4주째는 회복 주(최근 4주 고점의 75%), 회복 주 다음 주는 고점으로 복귀, 나머지 두 주는 완주 준비 계획 +10%, 기초 훈련 계획 +5% | `TE-S01`, `TE-S02` |
| 거리의 단위 | 0.1km, 내림. 다음 주의 기준은 내림한 실제 값이다 | `TE-S01`, `TE-S13` |
| 한 번의 최소 거리 | 2km. 더 짧아지면 그 주의 횟수를 줄인다(최소 2회) | `TE-G04` |
| 횟수별 구성(`long` / `easy` 한 번) | 2회 50% / 50%, 3회 45% / 27.5%, 4회 37% / 21%, 5회 32% / 17% | `TE-S03` |
| `tempo` | 완주 준비 계획, 초급 이상, 주 3회 이상, 주간 거리를 늘리는 주에만 `easy` 한 번을 같은 거리로 바꾼다. `long`과 이틀 이상 떨어진 요일에만 둔다 | `TE-S07`, `TE-S04` |
| 요일 | `long`은 일요일 → 토요일 → 마지막 선호 요일 순. 나머지는 간격이 가장 넓은 선호 요일 | `TE-G04` |
| 도달 기준 거리 | 5km는 4km, 10km는 8km, 하프마라톤은 16km. 조정 주를 뺀 주의 `long`으로 판정한다 | `TE-G06` |
| 기초 훈련 계획 | 도달 조건 없음, 증가율 +5%, `tempo` 없음. 시간 기반으로 시작하는 계획은 항상 기초 훈련 계획이다 | `TE-G06` |
| 조정 주 | 5km·10km는 대회가 있는 주, 하프마라톤은 그 전 주까지. 대회가 있는 주는 고점의 60%로 `easy`만, 하프마라톤의 전 주는 75% | `TE-G02`, `TE-S08` |
| 대회가 월~수요일 | 그 전 주도 대회가 있는 주처럼 줄인다. 검증기도 그 전 주에 같은 기준(고점보다 25% 이상 적음)을 적용한다 | `TE-S08` |
| 대회가 표준 기간보다 멀다 | 앞은 유지 주간(늘리지 않고 4주째마다 회복 주). 도달에 주가 더 필요하면 늘리는 주를 앞당긴다 | `TE-G07` |
| 시간 기반 계획 | 모두 `walk_run`, 한 번 30분(걷기 포함), 주 3회 이하. 한 번에 달리는 시간은 1 → 2 → 3 → 5 → 8 → 10 → 15 → 20 → 30분으로 한 주에 한 단계. 시작 단계는 10분 미만 1분, 10~30분 10분, 그 이상 30분 | `TE-S14` |
| 시간 기반 → 거리 기반 | 한 계획 안에서 잇지 않는다. 최근 14일에 30분 단계의 훈련에 연결된 기록이 3건 이상이면 그 거리 합계 ÷ 2를 최근 주간 거리로 삼아 계획을 다시 만들 수 있다. 6km 미만이면 시간 기반을 유지한다 | `TE-S14` |
| 계획을 시작하는 주 | 정해진 요일이 모두 내일 이후면 이번 주, 아니면 다음 주 월요일. 대회가 이번 주면 이번 주 | `TE-G09` |
| 권장 페이스 | 최근 페이스 대비 `easy`·`long`은 10~25% 느리게, `tempo`는 같거나 5%까지 느리게. 최근 페이스가 없으면 범위를 주지 않는다 | §7.2 |
| 무리한 목표 기록 | 목표 페이스가 최근 페이스보다 5km 15%, 10km 10%, 하프마라톤 5% 넘게 빠르면 경고한다. 최근 페이스가 없으면 확인하지 못했다고 알린다. 계획은 달라지지 않는다 | `TE-G06` |

바꾸지 않은 것: `TE-S01`의 적은 주간 거리 예외(두지 않는다), `TE-S13`의 실제 기록 기준, 컨디션에 따른 증가, 기존 `SAFETY` 값.

- 가입한 주에 훈련이 없을 때의 홈 화면 안내(`T-205`).

## 2026-11-17 — "목표 없음" 목표 추가 (F03-R01, D-04 일부)

온보딩에서 목표 거리를 반드시 골라야 해서, 정한 목표 없이 달리기를 시작해 보려는 사용자가 맞지 않는 목표를 골라야 했다. 개발자가 아래와 같이 정했다. 3km 기초 계획을 두자는 처음 제안은 쓰지 않는다. `D-04`는 여전히 확정이 아니며 9주는 초기값이다.

## 2026-11-17 — 무료는 맛보기: 가입 체험분과 이용 한도 변경 (D-08), 이미지 첨부 제외

무료 월 10회로는 일정 변경 대화를 3~4번 하면 끝나 코치의 가치를 판단하기 전에 막힌다는 문제에서 출발했다. 하루 단위 한도, 평생 체험분만 주기, 토큰 차감, Pro 기간 체험을 견주어 보고 개발자가 "가입 체험분 + 적은 월 한도"로 정했다. 무료 요금제의 AI 기능은 맛보기다.

| 항목 | 결정 | PRD |
|---|---|---|
| 무료의 구조 | 가입할 때 한 번 주는 체험분을 먼저 쓰고, 다 쓰면 월 한도에서 차감한다. 체험분은 기한이 없고 다시 채워지지 않는다 | §8.1, §8.2 |
| 한도의 단위 | 월 단위를 유지한다. 하루 단위로 바꾸지 않는다 | §8.2 |
| 이미지·파일 첨부 | MVP에서 제외한다. 채팅은 500자 이하의 글자만 받는다 | §1.4, `F04-R09` |
| 세는 단위 | 사용자에게는 횟수로 보여 준다. 토큰이나 크레딧으로 세지 않는다. 메시지 한 건의 비용은 글자 수 제한, 컨텍스트 구성, 출력 토큰 제한, 도구 호출 반복 제한으로 묶는다 | §6.8 |
| 확인 질문의 답 | 따로 묶지 않고 메시지마다 1회로 센다 | §8.2 |
| 무료 체험 기간 | 두지 않는다(`D-10` 그대로) | §8.4 |

수치(모두 초기값. Claude Code가 제안했고 개발자 확인이 필요하다):

| 항목 | 무료 | Pro |
|---|---|---|
| 가입 체험분 | AI 대화 30회, AI 일정 변경 3회 | 해당 없음 |
| AI 대화 | 체험분을 다 쓴 뒤 월 5회 | 월 300회(전에는 100회) |
| AI 일정 변경 | 체험분을 다 쓴 뒤 월 1회 | 월 30회 |

수치의 근거는 추정이다. 메시지 한 건에 입력 약 9,000토큰, 출력 약 400토큰으로 잡으면 가장 작은 모델 등급(입력 $0.10, 출력 $0.50 / 100만 토큰)에서 약 1.5원, 중간 등급에서 약 12원, 상위 등급에서 약 31원이다. 무료 가입자의 최대 비용은 첫 달 35건으로 50~1,100원, 이후 매월 5건으로 8~160원이다. Pro 300건은 460~9,300원이며, 상위 등급을 쓰게 되면 수입(약 6,700원)을 넘으므로 한도를 낮춰야 한다. `T-407`에서 잰 값으로 확정한다. 시스템 지침과 도구 정의가 아직 없어 토큰 수는 어림값이고, OpenAI의 가격은 공식 가격표가 아닌 자료로 봤다.

함께 넣은 것(개발자가 제안했고 Claude Code가 조건을 붙였다. 개발자 확인이 필요하다):

- 놓친 훈련이 많은 주의 일정 변경은 차감하지 않는다. 채팅의 일정 변경 제안을 만드는 시점에 이번 주 미완료 훈련이 2회 이상이고 이번 주에 이 조건으로 승인한 변경이 없을 때다. 서버가 훈련 상태로 판정하고 주 1회다. MVP의 코치는 먼저 말을 걸지 않으므로 "코치가 먼저 제안"은 홈의 미완료 안내로 들어온 대화를 가리키며, 진입 경로를 따로 기록하지 않고 위 조건만 본다.

문서를 고치면서 Claude Code가 정한 것(개발자 확인 필요):

- 체험분의 사용량은 새 테이블 `usage_trials`에 둔다. `usage_counters`의 월 키를 그대로 두기 위해서다.
- Usage 응답에 `pool`(`trial` / `month`)을 더했다. 한도 안내 카드는 월 한도까지 다 썼을 때만 나온다.
- Pro인 동안에는 체험분이 줄지 않고, 무료로 돌아오면 남은 만큼 쓸 수 있다.
- `change_proposals`에 `quota_exempt`를 더했다.
- 구현 작업: 체험분은 `T-410`(이용량 모듈 담당인 Codex), 차감 없는 일정 변경은 `T-403`(Claude Code).
- PRD §8.2 제목의 [제안]을 §15의 `D-08` 상태(확정)에 맞췄다.

아직 정하지 않은 것:

- 나중에 이미지를 받게 될 때의 차감 방식(Pro 전용 또는 여러 회 차감).

탈퇴 뒤 다시 가입한 계정(개발자 결정): 체험분을 다시 주지 않는다. 같은 사용자인지는 로그인 계정으로 판단한다.

| 항목 | 결정 |
|---|---|
| 같은 사용자의 판단 | 로그인 공급자와 공급자가 준 사용자 식별자를 서버 비밀값으로 해시한 값(`identity_hash`)이 같으면 같은 사용자다. 이메일과 이름은 지금처럼 저장하지 않는다 |
| 탈퇴할 때 남기는 것 | `usage_trials`의 해시와 체험분 사용 횟수뿐이다. 프로필, 계획, 기록, 대화는 지금처럼 바로 지운다(`DI-11`) |
| 다시 가입했을 때 | 같은 행을 이어 쓴다. 탈퇴 전에 쓴 횟수에서 이어진다 |
| 보존 기간 | 탈퇴 뒤 1년(초기값). 지나면 내부 작업이 지운다 |

개발자는 "탈퇴해도 데이터를 바로 지우지 말자"고 했으나, Claude Code가 개인 데이터는 바로 지우고 해시와 횟수만 남기는 것으로 좁혀 제안했다(개발자 확인 필요). 계정 삭제 때 개인 데이터를 지우는 것은 `F01-R06`, `DI-11`의 요구이고 스토어의 계정 삭제 기준과도 닿아 있으며, 탈퇴 뒤 보존 항목은 법률 검토(`D-12`) 대상이라 넓게 남기는 쪽을 먼저 정할 수 없다. 해시와 보존 기간도 `D-12`에서 확인하고 개인정보 처리방침에 적는다(`D-A5`).

확인할 것: 인증 서비스의 토큰에서 공급자의 사용자 식별자를 얻을 수 있는지는 인증 연결(`T-106`) 때 본다. 얻을 수 없으면 다른 방법을 다시 정한다. 월 한도(`usage_counters`)는 지금처럼 탈퇴하면 지워지므로, 탈퇴와 재가입을 되풀이하면 그달의 월 한도(대화 5회)는 다시 받는다.

코드: `packages/shared`의 `PLAN_LIMITS`를 새 값으로 고치고 `TRIAL_LIMITS`를 더했다. 이용량 모듈은 아직 체험분을 쓰지 않으므로 `T-410` 전까지 무료는 월 5회·1회로만 동작한다.
