## 0. 문서 사용 규칙

1. 화면의 기능 요구사항은 `PRD.md` §5가 기준이다. 이 문서는 그 화면을 **어떤 모양과 구성으로 만드는지**를 정한다.
2. 색, 간격, 글자 크기, 모서리 값은 §3의 토큰만 쓴다. 화면 코드에 색상 값이나 숫자를 직접 쓰지 않는다.
3. 화면은 §4의 컴포넌트로 조립한다. 목록에 없는 컴포넌트가 필요하면 먼저 제안한다.
4. 이 문서에서 정해야 하는 선택은 §12에 `UX-nn`으로 모았다. 확정과 대기는 §12의 표에 나눠 적는다.

## 1. 디자인 시스템 방침

### 1.1 자체 디자인 시스템

이 앱은 외부 디자인 시스템이나 UI 컴포넌트 라이브러리를 쓰지 않고 **자체 디자인 시스템**을 둔다. 토큰(§3)과 컴포넌트(§4)를 이 문서가 정의하고, `apps/mobile/src/ui/`에 직접 구현한다.

| 방침 | 내용 |
|---|---|
| 토큰의 기준 | 이 문서의 §3이다. 구현은 `apps/mobile/src/ui/tokens.ts` 파일 하나이며, 값을 바꿀 때는 이 문서와 그 파일을 함께 고친다 |
| 컴포넌트 | MVP 화면에 필요한 것만 만든다(§4). React Native의 기본 스타일 기능과 토큰만 쓴다 |
| 의존성 | 디자인 시스템을 위한 패키지를 추가하지 않는다 |
| 범위 | 이 앱 하나다. 다른 제품과 공유하거나 패키지로 배포하지 않는다 |
| 키우는 방식 | 화면에서 같은 모양이 두 번 필요해지면 컴포넌트로 올린다. 쓸 곳이 없는 컴포넌트를 미리 만들지 않는다 |

### 1.2 이렇게 정한 이유

Astryx 디자인 시스템(https://astryx.atmeta.com/)의 적용을 검토했다(2026-11-14).

- Astryx는 웹 전용이다. `react-dom`과 StyleX, 최신 브라우저 CSS 기능이 필요해서 React Native + Expo(`D-01`)에서는 컴포넌트가 실행되지 않는다.
- 토큰 값만 뽑아 쓰는 방식은 가능했다. 하지만 컴포넌트는 어차피 직접 만들어야 하고, 데스크톱 밀도에 맞춰진 기본값(본문 14px, 버튼 28~36px)도 모바일에 맞게 다시 정해야 했다. 베타 단계의 외부 패키지에 토큰을 묶어 둘 이유가 남지 않는다.
- 그래서 개발자가 자체 디자인 시스템으로 결정했다. 값과 이름은 이 프로젝트가 정하고, Astryx의 토큰·테마·패키지를 쓰지 않는다.

### 1.3 설계 기준

| 기준 | 내용 |
|---|---|
| 다크 기본 | 기본 테마는 다크다. 바탕은 남색이고, 그 위에 패널을 2~3단계로 쌓아 깊이를 준다(§3.2, §3.7). MVP는 다크로 고정한다(`UX-03`) |
| 포인트 색은 주황 하나 | 주황(`accent`)은 주 버튼, 진행 표시, '오늘' 표시에만 아껴 쓴다. 그 밖의 색은 훈련 종류(§8.1)와 상태(§8.2)에만 쓴다. 화면에 색이 보이면 뜻이 있다 |
| 숫자가 주인공 | 거리와 진행률 숫자는 크고 굵게(`display`) 보여 준다 |
| 모바일 밀도 | 본문 17, 터치 영역 44 이상, 화면 좌우 여백 16 |
| 4 단위 간격 | 모든 여백과 간격은 4의 배수다 |
| 패널 단계로 구분 | 카드와 입력창은 바탕보다 한 단계 밝은 패널로 구분한다. 1px 테두리(`border`)는 구분선과 입력창에만 쓴다 |
| 선 아이콘, 이모지 없음 | 아이콘은 직접 그린 선 아이콘만 쓴다(§8.3). 화면 문구와 시스템 메시지에 이모지를 쓰지 않는다 |
| 대비 | 글자는 4.5:1 이상, 아이콘과 색 점은 3:1 이상이다. 다크와 라이트 모두 `tokens.test.ts`로 검사한다 |

## 2. 디자인 원칙

`PROJECT_CONTEXT.md` §7.3의 UX 원칙 6개가 우선하고, 그 위에 아래 원칙을 둔다.

| # | 원칙 | 실천 |
|---|---|---|
| 1 | 컴포넌트 우선 | 화면 코드에서 기본 요소(`View`, `Text`)에 직접 스타일을 입히지 않는다. §4의 컴포넌트를 조립한다 |
| 2 | 의미 토큰만 사용 | `text.primary`, `background.surface`처럼 역할로 이름 붙은 토큰만 쓴다. 색상 값과 숫자를 직접 쓰지 않는다 |
| 3 | 값이 한 곳에만 있는 코드 | 강조색이나 글자 크기를 바꿔도 화면 코드는 그대로다. 토큰 파일만 고친다 |
| 4 | 화면 틀 먼저 | 화면의 틀(머리글, 본문, 하단 고정 영역)을 먼저 잡고 내용을 채운다 |
| 5 | 목록은 행으로 | 훈련 목록, 기록 목록처럼 같은 종류가 반복되는 것은 구분선이 있는 행으로 보여 준다. 카드는 오늘의 훈련, 변경 제안, 요약처럼 독립된 덩어리에만 쓴다 |
| 6 | 상태는 점과 칩으로 | 완료·예정·미완료·생략은 상태 점과 글자가 있는 칩으로 표시한다. 숫자 배지는 개수에만 쓴다 |
| 7 | 색만으로 구분하지 않는다 | 상태와 훈련 종류는 색에 더해 아이콘이나 글자를 함께 쓴다 |
| 8 | AI가 할 일을 먼저 보여 준다 | 데이터가 바뀌는 일은 항상 변경 전후를 카드로 보여 주고 버튼으로 확정한다(`F05-R03`, `F05-R04`) |

## 3. 디자인 토큰

### 3.1 토큰 정의

- 토큰은 `apps/mobile/src/ui/tokens.ts` 한 파일에 다크와 라이트 값을 함께 정의한다. 컴포넌트는 `useTheme()`으로 현재 모드의 값을 받는다.
- 다크와 라이트는 같은 토큰을 짝으로 가진다. 배치와 문구는 같고 색 값만 다르다. MVP는 다크로 고정하고 라이트는 값만 준비한다(`UX-03`).
- 토큰 이름과 값은 Figma의 변수와 맞춘다. 변수 묶음 'PaceMate · C2 tokens'에 다크 색 31개와 간격·모서리·크기 숫자 21개, 'PaceMate · C2 tokens (Light)'에 라이트 색 31개가 있다(2026-11-18 디자이너 수정 기준). 내보낸 값은 [`docs/design-tokens/`](design-tokens/README.md)의 JSON에 있다. 아래 표가 기준이고, JSON과 다르면 표를 따른다. 옮길 때 대비 검사를 통과하지 못하는 값은 고치기 전에 개발자에게 알린다.
- Figma의 색 31개는 아래 표의 색과 같다. `hero/from`, `hero/to`는 표의 `hero.from`, `hero.to`다. 2026-11-18 디자이너 수정으로 Figma에 `background/raised`, `text/accent`가 생기고 `onAccent`가 남색이 되었다. `docs/design-tokens/`의 JSON은 디자이너가 올리는 PR로 새 값(색 31개)이 된다. 그 전의 JSON은 `onAccent`가 흰색이고 두 변수가 없으니 이 표를 따른다.
- Figma의 C2 컴포넌트는 색이 변수에 연결되지 않고 값으로 들어가 있다. 컴포넌트에서 읽은 값이 아니라 토큰 이름과 변수 값을 기준으로 구현한다. 컴포넌트의 값이 변수와 다르면 변수를 따르고 차이를 알린다.
- 토큰 이름은 역할을 말한다(`color.text.primary`). 색 이름(회색, 파랑)으로 부르지 않는다.
- 아래 표의 값이 기준이다. 값을 바꾸면 이 문서와 토큰 파일을 함께 고치고, 색을 바꿀 때는 대비(§1.3)를 다시 확인한다.

- 주황은 포인트 색 하나뿐이다. 주 버튼, 진행 표시(`ProgressBar`, `WeekGauge`), '오늘' 표시에만 쓰고 장식에 쓰지 않는다.

- `onAccent`는 흰색이 아니라 남색이다. 흰 글자는 주황 위에서 대비가 4.5:1에 못 미친다(다크 `#FF5A1F`에서 3.12:1, 라이트 `#EE4F14`에서 3.64:1). 남색 `#0B1018`은 다크 주황 위에서 6.11:1, 라이트 주황 위에서 5.23:1이다. Figma 변수도 2026-11-18에 남색으로 고쳤다(`UX-15`).
- 표의 글자색은 바탕·카드·패널(`background.raised`) 위에서 모두 4.5:1 이상이다. 예외는 `text.disabled`다. 다크는 패널 위 4.20:1, 라이트는 바탕 위 4.33:1, 패널 위 4.21:1이다. 비활성 글자는 대비 기준(WCAG 1.4.3)의 예외라 그대로 두고, 대비 검사(`tokens.test.ts`)도 `text.disabled`를 검사하지 않는다.
- 라이트의 회색 설명 글자(`text.secondary`)는 `#4A5463`으로, 바탕 `#F4F5F7`에서 7.03:1이다.

| 옅은 채움과 그 위의 글자 | `successMuted` + `text.success` | 안내 띠(배너), 상태 칩 |

|---|---|---|
| success | `#5FD39A` / `#12784A` | `#163329` / `#E2F4EA` |

라이트 색 31개는 Figma에 준비만 되어 있고 MVP에서는 쓰지 않는다(`UX-03`).

강조색은 주황이다(`UX-01`). 강조색을 바꿀 때는 `accent`, `onAccent`, `accentMuted`, `text.accent`를 함께 바꾸고, `onAccent`와의 대비가 4.5:1 이상인지, 훈련 종류 색(§8.1)과 헷갈리지 않는지 확인한다.

### 3.3 간격

4px 단위다. 여백과 간격에는 이 값만 쓴다.

| 토큰 | 값 | 주 용도 |
|---|---|---|
| `spacing.1` | 4 | 아이콘과 글자 사이 |
| `spacing.2` | 8 | 칩 안쪽, 가까운 요소 사이 |
| `spacing.3` | 12 | 행 안의 요소 사이, 목록 항목 사이 |
| `spacing.4` | 16 | **화면 좌우 여백, 카드 안쪽 여백** |

그 밖에 `spacing.0`(0), `0.5`(2), `1.5`(6), `5`(20), `7`(28), `9`~`12`(36~48)가 있다. Figma 변수(`space/*`)에는 0, 2, 4, 8, 12, 16, 20, 24, 32, 40, 48만 있다. 6, 28, 36, 44는 Figma에 없으므로 시안에서 쓰는 곳이 나오면 이 표에 남길지 정한다.

### 3.7 그림자와 테두리

카드와 입력창은 테두리 대신 패널 단계로 구분한다: 바탕(`background.body`) → 카드(`background.surface`) → 카드 안의 패널(`background.raised`). 1px 테두리(`border`)는 구분선과 입력창에만 쓴다. 그림자는 바탕 위에 떠 있는 것에만 쓴다. 다크 바탕에서는 그림자가 잘 보이지 않으므로, 떠 있는 것도 패널 단계로 먼저 구분한다.

| 단계 | 쓰는 곳 |
|---|---|
| 낮음 | 화면 하단 고정 버튼 영역 |
| 중간 | 토스트 |
| 높음 | 하단 시트, 대화 상자 |

값은 구현 시 iOS와 Android의 그림자 방식에 맞춰 토큰 파일에 직접 정의한다.

### 4.4 컴포넌트 규칙

1. 색, 간격, 글자 크기를 속성으로 받지 않는다. `variant`, `size`, `status`처럼 뜻이 있는 속성만 받는다.
2. 누를 수 있는 것은 모두 눌림 표시가 있고 터치 영역이 44×44 이상이다.
3. 서버에서 데이터를 받는 컴포넌트는 로딩(자리 표시), 빈 상태, 오류 상태를 가진다.
4. 입력 컴포넌트는 값과 변경 함수를 밖에서 받는다.
5. 접근성 이름과 역할을 컴포넌트 안에서 지정한다(§10).

## 6. 화면별 설계

기능 요구사항과 예외는 PRD §5의 같은 화면 절에 있다.

### 6.1 인트로, 로그인, 동의, 온보딩 시작

- 인트로: 3장. 가운데에 그림과 제목·한 줄 설명, 아래에 장 위치 표시(점 3개)와 주 버튼 [다음]. 옆으로 넘겨도 된다. 마지막 장의 주 버튼은 [시작하기]이고 로그인으로 간다. 기기마다 처음 한 번만 보여 준다(PRD `F01-R08`). 각 장의 그림과 문구는 Figma에서 정한다.
- 로그인: 화면 가운데에 서비스 이름과 한 줄 소개, 하단에 Apple 로그인 버튼, Google 로그인 버튼. 카카오 로그인은 MVP에서 뺐다(PRD `F01-R01`, `UX-14`). 각 서비스의 로그인 버튼 지침(모양, 색, 문구)을 따른다. 문구는 "Apple로 계속하기", "Google 계정으로 계속하기"다. Apple 버튼은 C2 시안처럼 다크 바탕에 흰색이다. Google 버튼은 Google 지침의 다크 테마 버튼(바탕 `#131314`, 테두리 `#8E918F`, 글자 `#E3E3E3`, 컬러 G 로고)을 쓴다. 두 버튼은 높이와 모서리를 같게 맞춘다. 로그인 서비스가 정한 색은 화면 코드에 쓰지 않고 토큰 파일에 따로 둔다(§3).
- 동의: 필수 항목 3개를 `ListItem`과 체크로 나열한다. 각 항목에 [전문 보기]. 맨 위에 "모두 동의". 세 항목이 모두 체크되어야 하단 주 버튼이 활성화된다.
- 온보딩 시작: 제목(예: "나에게 맞는 훈련 계획을 만들어 볼까요?")과 "2분이면 끝나요" 같은 짧은 설명, 하단 주 버튼 [시작하기], 글자 버튼 [나중에 할게요]. [나중에 할게요]는 계획 없는 홈으로 가고, 고른 사실은 기기에 저장한다(PRD `F02-R08`).

### 6.2 온보딩

- 한 화면에 질문 하나. 위쪽에 `Stepper`(진행률)와 뒤로 가기, 가운데에 질문(`title1`)과 선택지, 하단에 [다음].
- 선택지는 `SelectableCard`로 세로 나열한다. 선택하면 바로 다음으로 넘어가지 않고 [다음]을 눌러야 넘어간다.
- 숫자 입력(주간 거리, 최근 기록)에는 "잘 모르겠어요"를 글자 버튼으로 둔다.
- 요일 선택은 요일 7개를 한 줄에 원형 버튼으로 놓는다. 가능 횟수보다 적게 고르면 [다음]이 비활성이고 이유를 보조 글자로 알린다.
- 선택 항목(목표 기록, 대회 날짜)에는 [건너뛰기].
- 목표 거리의 마지막 선택지는 "아직 목표가 없어요"(보조 글자 "가볍게 시작하고 싶어요")다. 고르면 목표 기록과 대회 날짜 화면 없이 계획 생성으로 넘어가고, `Stepper`의 전체 단계 수도 줄어든다(`F02-R07`).
- 온보딩은 9문항이다(목표 없음이면 7문항). 키와 몸무게는 묻지 않는다.
- 계획 생성 중에는 `Spinner`와 "계획을 만들고 있어요".
- 계획 미리보기: 요약 `StatTile` 3개(전체 주 수, 주당 횟수, 종료일) → 경고가 있으면 `Banner`(warning) → 첫 주 일정 `SessionRow` 목록(날짜를 함께 보여 준다. 예: "월 11/17", `UX-11`) → 하단 [이 계획으로 시작], 글자 버튼 [답변 수정].
- 완주 준비 계획과 기초 훈련 계획을 모두 만들 수 있으면 미리보기 위에 `SelectableCard` 두 개로 고르게 한다. 고른 계획의 요약과 첫 주 일정이 아래에 보인다. 하나만 만들 수 있으면 선택 없이 그 계획을 보여 주고, 완주 준비 계획을 만들 수 없는 이유를 `Banner`(info)로 알린다. 목표 없음이면 선택 카드와 `Banner` 없이 기초 훈련 계획 하나를 보여 주고, 요약 위에 목표 문구(`focus`)를 쓴다.

### 6.3 홈

```text
┌─────────────────────────────────┐
│ 안녕하세요                        │
│ 하프마라톤 · D-42                 │  display 숫자
│ ████████░░░░░░░  12 / 36 완료     │  ProgressBar
├─────────────────────────────────┤
│ ┌─ 오늘의 훈련 ────────────────┐  │  TodayCard
│ │ ● 가볍게 달리기               │  │
│ │ 5km · 편하게 대화할 수 있는 속도 │  │
│ │ [기록하기]                    │  │
│ └─────────────────────────────┘  │
│ ┌─────────────────────────────┐  │  매니저 메시지 (ClickableCard)
│ │ (coach) 어제 훈련을 놓쳤어요.   │  │
│ │    이번 주 일정을 다시 짤까요?   │  │
│ └─────────────────────────────┘  │
│ 이번 주                          │  Section
│   ◠ 1 / 3회   월 ▮ 수 ▯ 토 ▯      │  WeekGauge
│ 월 ● 가볍게 달리기 5km      완료   │  SessionRow
│ 수 ● 조금 빠르게 달리기 6km  예정   │
│ 토 ● 길게 달리기 12km       예정   │
└─────────────────────────────────┘
```

- `TodayCard`는 등고선 무늬와 주황 경로선이 있는 카드다. 거리 숫자를 `display`로 크게 쓴다. '오늘' 표시는 `accent`다.
- 이번 주 구역 위에 `WeekGauge`를 둔다. 반원 게이지는 이번 주 완료 횟수 / 계획 횟수, 막대는 요일별 계획과 완료다.
- 오늘 훈련이 없으면 `TodayCard`에 "오늘은 쉬는 날이에요"를 보여 준다.
- 오늘 훈련을 이미 기록했으면 버튼 대신 완료 표시와 기록 요약을 보여 준다.
- 매니저 메시지를 누르면 AI 코치로 이동한다.
- 어제 훈련 기록 카드: 어제 훈련이 있었는데 기록이 없으면 `TodayCard` 아래에 `Card`로 보여 준다. 제목 "어제 훈련을 기록하지 않았어요", 훈련 한 줄(`SessionRow`), 버튼 [기록하기](주)와 [못 했어요](보조). [기록하기]는 날짜와 연결할 훈련이 채워진 기록 입력을 연다. [못 했어요]는 카드를 닫고, 닫은 훈련 ID를 기기에 저장한다. 훈련 상태는 바꾸지 않는다. 이틀 전 훈련에는 카드를 보여 주지 않는다(응답의 `yesterdaySession`).
- 이번 주 미완료 훈련이 2회 이상이면(응답의 `weekMissedCount`) 어제 훈련 기록 카드 아래, 카드가 없으면 매니저 메시지 자리에 글자 버튼 [코치와 일정 조정하기]를 둔다. 누르면 AI 코치를 열고 입력창에 "이번 주 훈련을 두 번 놓쳤어요. 일정을 조정해 줘"를 채운다. 자동으로 보내지 않는다(PRD `F05-R14`).
- 놓친 훈련 문구는 탓하지 않는다(§9.1). 몰아서 보충하라고 하지 않는다.
- 첫 홈은 세 가지 상태다(PRD §5.4).
  - 계획 없음(온보딩을 건너뛰었거나 계획을 확정하지 않음): 계획 만들기 카드(`ClickableCard`, "나에게 맞는 훈련 계획을 만들어 보세요")가 화면의 중심이다. 누르면 온보딩으로 간다. AI 코치 바로가기는 그대로 둔다.
  - 이번 주 시작: 위 그림과 같다.
  - 다음 주 시작: D-day 영역에 "시작까지 D-n"과 시작 날짜, `TodayCard` 자리에 준비 안내(예: "다음 주 월요일부터 시작해요. 첫 주 일정을 미리 살펴보세요"). 이번 주 목록 대신 첫 주 훈련 목록을 보여 준다. 문구는 서버의 매니저 메시지(`PLAN_NOT_STARTED`)를 쓴다.
- 활성 계획이 없으면(끝난 계획도 없음) 위의 계획 만들기 카드를 보여 준다. 프로필이 있으면 누를 때 온보딩 대신 목표 선택부터 시작한다.
- 계획이 끝났으면 `EmptyState`에 버튼을 둘 둔다: [이어서 훈련하기](주 버튼)와 [새 목표 설정](보조 버튼). [이어서 훈련하기]는 질문 없이 유지 계획의 미리보기로 간다(`F03-R08`, `F03-R10`). 끝난 계획이 없으면 [새 목표 설정]만 둔다.
- 유지 계획은 목표 없음 계획과 같이 목표 문구("꾸준히 달리는 습관 만들기")와 진행 상황을 보여 준다. 유지 계획임을 따로 표시할지와 그 형태는 Figma에서 정한다(`T-207`).
- 대회 날짜가 없으면 D-day 대신 "N주차 / 전체 M주"를 보여 준다.
- 목표 없음이면 목표 대회와 D-day 영역을 숨기고, 그 자리에 목표 문구(응답의 `focus`: "30분 쉬지 않고 달리기" 또는 "꾸준히 달리는 습관 만들기")와 진행 상황을 보여 준다. 진행 상황의 예: "지금 5분 달리기, 30분까지 4단계 남았어요", 이번 주에 달린 횟수. 정확한 형태는 Figma에서 정하고, 응답에 필드가 더 필요하면 `T-205`에서 `API_SPEC.md`를 먼저 고친다. "3km 달리기"처럼 계획이 정하지 않은 거리를 문구에 넣지 않는다(`F03-R09`).
- 목표 없음 계획이 끝나면 `EmptyState`의 문구가 다음 목표를 권한다("5km에 도전해 볼까요?"). 버튼 구성은 위와 같다(`F03-R08`).

- 한도에 도달하면 입력창 위에 `LimitCard`가 대화의 마지막에 나타나고, 입력창은 그대로 둔다(다시 보내면 같은 안내가 나온다).

### 6.5 캘린더

```text
┌─────────────────────────────────┐
│ 캘린더               [주간|월간]  │  SegmentedControl
├─────────────────────────────────┤
│ ‹  11월 3주차 (16일~22일)  ›      │

│ 16  17  18 [19] 20  21  22       │  오늘은 테두리, 선택일은 채움
│ ●       ●   ●                   │  훈련 종류 색 점
├─────────────────────────────────┤
│ 11월 19일 (목)                    │
│ ● 길게 달리기 12km   변경됨 · 예정  │  SessionRow → 누르면 훈련 상세
└─────────────────────────────────┘
```

- 주간 보기는 좌우로 쓸어 주를 넘긴다. 월간 보기는 `MonthGrid`이고 날짜를 누르면 아래 목록이 바뀐다.
- 훈련이 없는 날을 고르면 "쉬는 날이에요".
- 날짜 칸의 표시: 예정은 종류 색 점, 완료는 체크, 미완료는 빈 테두리 점, 생략은 표시 없음.
- 훈련 상세는 `BottomSheet`다: 종류 칩과 상태 칩 → 거리·권장 강도 → 설명 → 변경된 훈련이면 "원래 일정: 11월 21일 (토)" → 연결된 기록 또는 [기록하기] → 글자 버튼 [AI에게 변경 요청].

### 6.6 운동 기록

- 기록 탭: `StatTile` 2×2(이번 주 거리·횟수, 이번 달 거리·횟수) → 주간 분석 `SummaryCard` → 기록 목록(`WorkoutRow`, 월별 구역 제목) → 오른쪽 위 [+].
- 주간 분석 카드: 완료 횟수 / 계획 횟수, 총 거리, 달성률 `ProgressBar`. Pro는 그 아래에 AI 피드백 문장, 무료는 "Pro에서 AI 피드백을 받아 보세요" 한 줄과 화살표.
- 기록 입력(전체 화면): 날짜 → 거리 → 시간 → 자동 계산된 페이스(읽기 전용) → 운동 강도 `ScaleInput`(선택) → 통증(선택) → 연결할 훈련 `Selector` → 하단 고정 [저장]. 컨디션은 받지 않는다(PRD `F07-R01`).
- 통증은 "통증이 있었나요?"에 [없었어요] / [있었어요]를 `SegmentedControl`로 두고, [있었어요]를 고르면 `TextArea`("어디가 어떻게 아팠는지 적어 주세요", 500자)가 열린다. 적은 내용은 기록의 `memo`로 저장한다.
- 저장하면 기록 입력을 닫고 결과 시트(`BottomSheet`)를 띄운다: 코치 한마디(서버가 준 템플릿 문구) → 이번 주 진행률("이번 주 2/3회"와 `ProgressBar`) → 주 버튼 [확인]. 활성 계획이 없으면 진행률을 뺀다(PRD `F07-R10`). 통증을 적었으면 코치 한마디는 쉬기를 권하는 문구다.
- 거리와 시간은 숫자 키패드로 받는다. 시간은 시·분·초 세 칸이다.
- 훈련 상세에서 들어오면 날짜와 연결할 훈련이 채워져 있다.
- 중복이나 비정상 페이스로 서버가 확인을 요청하면 `Dialog`로 묻는다(`WORKOUT_DUPLICATE`, `PACE_OUT_OF_RANGE`).

### 6.7 마이페이지

- `List`로 구성한다: 프로필·목표 → AI 코치(누르면 코치 바꾸기. 오른쪽에 지금 코치의 `CoachAvatar`와 이름) → 구독(현재 요금제, `UsageIndicator` 2개, 다음 초기화 날짜) → 알림 설정 → 약관·정책 → 문의 → 로그아웃 → 계정 삭제(위험 색).
- 목표 바꾸기: 내 목표의 [목표 바꾸기] → `Dialog`("목표를 바꾸면 남은 계획이 새로 만들어져요. 지금까지의 기록과 진행률은 그대로 남아요.", [바꾸기] / [취소]) → 온보딩의 목표 거리·목표 기록·대회 날짜 화면(같은 컴포넌트를 쓴다) → 앱에 쌓인 기록이 2주 미만이면 온보딩의 주간 거리 화면 한 장("요즘 일주일에 얼마나 달려요?") → 변경 미리보기(PRD `F02-R09`).
- 변경 미리보기는 채팅의 `ProposalCard`(목표 변경)와 같은 내용을 전체 화면으로 보여 주고 [이 계획으로 시작], [취소]. 목표를 안전한 수준으로 조정했으면 그 이유를 `Banner`(info)로 보여 준다(예: "대회까지 기간이 짧아서 완주를 목표로 잡았어요").
- 프로필을 수정하고 저장할 때도 같은 변경 미리보기를 쓰며, 버튼은 [적용하기], [취소]다.
- 계정 삭제는 삭제되는 내용과 구독 해지 안내를 보여 준 뒤 `Dialog`로 한 번 더 확인한다.
- 코치 바꾸기는 §6.10의 화면을 전체 화면으로 연다. 지금 코치가 골라진 상태로 열리고, 주 버튼은 [이 코치로 바꾸기]다. 바꾸면 `Toast`로 "다음 답변부터 수리가 함께해요"처럼 알리고, 이전 대화는 그대로 둔다.

### 6.8 페이월

- 위에서부터: 닫기 버튼 → 제목 → Pro 혜택 4줄(아이콘과 한 줄씩) → 요금제 `SelectableCard` 2개(연간이 기본 선택, 월 환산 금액 표시) → 주 버튼 [구독하기] → 글자 버튼 [구독 복원] → 자동 갱신·해지 안내와 약관 링크(`caption`).
- 가격은 스토어가 알려 준 값을 그대로 표시한다. 화면에 금액을 직접 쓰지 않는다.
- 결제 확인이 늦으면 "확인하고 있어요" 화면(`Spinner`, 설명 한 줄, 글자 버튼 [구독 복원])으로 바꾼다. 확인이 끝나면 완료 안내 뒤 페이월을 연 화면으로 돌아간다. 채팅의 한도 안내 카드에서 왔으면 하던 채팅으로 돌아간다(PRD `F10-R09`).

### 6.9 공통 상태

| 상태 | 표현 |
|---|---|
| 처음 로딩 | 실제 배치와 같은 모양의 `Skeleton`. 화면 전체 `Spinner`는 계획 생성처럼 기다림이 긴 경우에만 |
| 다시 불러오기 | 아래로 당기기. 기존 내용을 지우지 않는다 |
| 빈 상태 | `EmptyState`: 아이콘, 한 문장, 할 수 있는 일 버튼 하나 |
| 오류 | 화면 전체가 실패하면 `EmptyState`와 [다시 시도]. 일부 동작이 실패하면 `Toast` 또는 그 자리의 `Banner` |
| 네트워크 끊김 | 화면 위에 `Banner`(warning) "인터넷 연결을 확인해 주세요" |
| 업데이트 필요 | 닫을 수 없는 전체 화면과 스토어로 가는 버튼(`APP_UPDATE_REQUIRED`) |

### 6.10 코치 고르기

PRD `F04-R11`~`F04-R13`. 코치마다 다른 것은 AI 응답의 말투뿐이다(PRD `AI-11`). 계획, 변경 제안, 이용 한도, 화면 문구는 세 코치가 같다.

```text
┌─────────────────────────────────┐
│ 어떤 코치와 함께 달릴까요?          │  title1
│ 언제든 마이에서 바꿀 수 있어요       │  supporting
│ ┌─────────────────────────────┐ │  CoachSelectCard (선택됨)
│ │ (◉) 온이  다정한 러닝 친구      │ │
│ │ "오늘도 나와 줘서 고마워요."    │ │
│ └─────────────────────────────┘ │
│ ┌─────────────────────────────┐ │  CoachSelectCard
│ │ (◉) 수리  차분한 데이터 코치    │ │
│ └─────────────────────────────┘ │
│ ┌─────────────────────────────┐ │  CoachSelectCard
│ │ (◉) 번개  힘찬 스포츠 코치      │ │
│ └─────────────────────────────┘ │
│ [ 이 코치와 시작하기 ]             │  주 버튼, 하단 고정
└─────────────────────────────────┘
```

| 항목 | 설계 |
|---|---|
| 제목 | "어떤 코치와 함께 달릴까요?" |
| 카드 | `CoachSelectCard` 3장을 세로로 놓는다. 하나를 고른 뒤 [이 코치와 시작하기]를 누른다. 고르기 전에는 주 버튼이 비활성이다 |
| 프로필 이미지 | 셋 다 같은 캐릭터 가족의 입체 일러스트다. 배경이 투명한 PNG(3배 크기)로, 원형으로 자른 것과 캐릭터만 따낸 것 두 가지가 있다. 크기는 `CoachAvatar`(§4.3)를 따른다. 원형 이미지는 `apps/mobile/assets/coaches/{oni,suri,bungae}.png`에 1·2·3배(104·208·312px)로 있다. 캐릭터만 따낸 이미지는 같은 폴더의 `{oni,suri,bungae}-character.png`에 같은 크기로 있다. 두 이미지는 같은 1024px 캔버스에서 잘라 위치가 같다. 둘 다 가장 큰 크기 104에 맞췄고, 작은 크기는 기기가 줄여 그린다. 원형 이미지는 받은 JPEG에서 원형 밖을 투명하게 잘라 만들었다. 둥근 얼굴에 머리 위 더듬이가 있다. 온이는 헤어밴드를 하고 손을 흔든다. 수리는 안경을 쓰고 그래프 태블릿을 든다. 번개는 번개 모자에 호루라기를 걸고 있다. 이미지 파일은 앱에 넣는다(`D-A10`) |
| 말투 예시 | 카드마다 한 문장. 문구는 Figma에서 정한다. 예시 문장에도 훈련 수치를 넣지 않는다 |
| 기본 선택 | 처음 열면 아무것도 골라져 있지 않다. 온보딩을 건너뛰었거나 고르지 않은 사용자의 코치는 온이다(PRD `D-15`) |
| 저장 | [이 코치와 시작하기]를 누를 때 서버에 저장한다. 실패하면 화면에 남아 `Banner`(error)로 알리고 [다시 시도]를 둔다. 실패했는데 다음 화면으로 넘어가지 않는다 |
| 화면 낭독 | 카드마다 "온이, 다정한 러닝 친구, 선택됨"처럼 한 덩어리로 읽는다. 프로필 이미지는 장식으로 처리해 따로 읽지 않는다 |

| 값 | 이름 | 소개 | 말투(PRD `AI-11`) |
|---|---|---|---|
| `oni` | 온이 | 다정한 러닝 친구 | 다정한 해요체, 공감 먼저, 2~3문장 |
| `suri` | 수리 | 차분한 데이터 코치 | 정중한 해요체, 결과 → 근거 → 다음 할 일, 3~4문장 |
| `bungae` | 번개 | 힘찬 스포츠 코치 | 짧은 해요체 3~4문장, 핵심만 |

## 7. 채팅과 변경 제안

제품의 핵심 경험이다. 처리 흐름은 PRD §6에 있다.

### 7.1 대화

| 항목 | 설계 |
|---|---|
| 사용자 메시지 | 오른쪽, `background.muted` 말풍선, 모서리 `radius.chat` |
| AI 메시지 | 왼쪽, 말풍선 없이 본문 글자. 옆에 고른 코치의 `CoachAvatar`(30)를 둔다. 카드가 있으면 글자 아래에 붙는다 |
| 시스템 메시지 | 가운데, `caption`, `check` 아이콘과 한 줄(예: "일정을 변경했어요") |
| AI 말투 | 고른 코치의 말투로 답한다(PRD `AI-11`). 온이만 기분 좋은 순간에 이모지를 1개까지 쓸 수 있고, 앱은 이를 글자 그대로 보여 준다. 시스템 메시지와 카드에는 코치 말투와 이모지를 쓰지 않는다 |
| AI 글 표시 | 일반 글자로 표시한다. 마크다운을 해석하지 않으므로 시스템 지침에 마크다운을 쓰지 않도록 넣는다 |
| 응답 대기 | `TypingIndicator`. 입력창과 보내기 버튼 비활성(`CHAT_BUSY` 방지) |
| 응답 실패 | 사용자 메시지 아래에 `text.error` 색 "보내지 못했어요"와 [다시 보내기] |
| 날짜 구분 | 날짜가 바뀌는 곳에 날짜 구분선 |
| 이전 대화 | 위로 스크롤하면 이어서 불러온다 |
| 빠른 질문 | 입력창 위의 칩. 누르면 바로 전송한다 |
| 이용량 | 머리글 오른쪽에 표시한다. 가입 체험분을 쓰는 동안(응답의 `pool`이 `trial`)에는 "체험 대화 27회 남음"(남은 횟수), 다 쓰면(`month`) "이번 달 3/5"(사용/한도). 마이페이지에도 같은 형식과 같은 값으로 보여 준다. 누르면 구독 화면 |
| 훈련 지정 진입 | 훈련 상세의 [AI에게 변경 요청]으로 들어오면 입력창 위에 대상 훈련 칩("길게 달리기 · 11/21")을 보여 주고 X로 뗄 수 있다 |

### 7.2 변경 제안 카드

```text
┌─ (swap) 일정 변경 제안 ───────────┐
│ 길게 달리기 12km                 │  변경되는 훈련
│ 토 11/21  →  목 11/19            │  변경 전 → 변경 후
│ ─────────────────────────────  │
│ 가볍게 달리기 5km         [생략]  │  생략되는 훈련 (Chip)
│ 금 11/20                        │
│ ─────────────────────────────  │
│ 이번 주 거리  23km → 18km        │  영향 요약
│ (warning) 이번 주 훈련이 1회 줄어요 │  경고 (있을 때만, Banner)
│                                 │
│ 여행 일정(금~일)에 맞췄어요           │  이유 한 줄 (서버 템플릿)
│                                 │
│ [ 다른 방법 보기 ]   [ 적용하기 ]  │
│ AI 일정 변경 1/1회 사용 · 오늘 자정까지 │  caption
└─────────────────────────────────┘
```

| 카드 종류 | 제목 | 내용 | 승인 버튼 |
|---|---|---|---|
| 일정 변경 | 일정 변경 제안 | 훈련별 변경 전 → 후, 생략, 영향 요약, 이유 한 줄 | 적용하기 / 다른 방법 보기 |
| 목표 변경 | 목표 변경 제안 | 목표 변경 전 → 후, 바뀌는 훈련 수, 이후 주간 구성 요약, 조정한 이유(있을 때) | 이 계획으로 시작 / 취소 |
| 기록 등록 | 기록 확인 | 날짜, 거리, 시간, 페이스, 연결할 훈련 | 기록 저장 / 취소 |

카드의 상태 (`Proposal.status`와 대응)

| 상태 | 표현 |
|---|---|
| 대기 | 버튼 두 개 활성 |
| 승인 처리 중 | [적용하기]가 `Spinner`로 바뀌고 두 버튼 비활성 |
| 승인됨 | 버튼 자리에 `text.success` 색 `check` 아이콘과 "적용했어요", 글자 버튼 [캘린더에서 보기] |
| 취소됨 | 버튼 자리에 "취소한 제안이에요". 카드 전체를 흐리게 |
| 대체됨 | "새 제안으로 바뀌었어요". 흐리게 |
| 만료 | "이 제안은 만료됐어요. 다시 물어봐 주세요". 흐리게. 제안은 만든 날 자정에 만료된다(PRD `DI-05`) |
| 승인 실패 | 카드 안에 `Banner`(error)로 서버의 `message`를 보여 준다. 다시 요청해야 하는 실패(`PLAN_CHANGED` 등)면 버튼을 없애고, 일시적 실패면 [다시 시도] |
| 한도 초과 | 카드는 대기 상태로 두고 아래에 `LimitCard` |

설계 규칙:

1. 카드의 내용은 서버가 준 Proposal 객체로만 그린다. AI의 문장을 카드에 넣지 않는다.
2. 승인 버튼([적용하기], [이 계획으로 시작], [기록 저장])은 카드의 유일한 주 버튼이다. [다른 방법 보기]와 [취소]는 보조 버튼이다.
   - [다른 방법 보기]는 제안을 취소하고(차감 없음) 입력창에 "다른 방법도 알려 줘"를 채운다. 자동으로 보내지 않는다(PRD `F05-R13`).
3. 승인이 끝나면 햅틱 한 번과 시스템 메시지로 알린다. 화면을 자동으로 옮기지 않는다.
4. 변경 전후는 같은 줄에 화살표로 놓는다. 생략되는 훈련은 취소선 없이 "생략" 칩으로 표시한다(취소선은 읽기 어렵다).
5. 이용량이 차감되는 제안에는 버튼 아래에 이용량을 보여 준다: 체험분이면 "체험 일정 변경 2회 남음", 월 한도면 "AI 일정 변경 1/1회 사용". 만료 시각은 "오늘 자정까지"로 쓴다. 차감되지 않는 제안(기록 등록)에는 보여 주지 않는다. 놓친 훈련이 많은 주라 차감되지 않는 일정 변경에는 "이번 변경은 횟수를 쓰지 않아요"를 보여 준다.

### 7.3 한도 안내 카드

가입 체험분과 이번 달 한도를 모두 썼을 때 나온다. 입력창은 그대로 둔다(§6.4).

체험분만 다 썼을 때는 카드를 띄우지 않는다. 마지막 체험분을 쓴 응답 아래에 `ChatSystemMessage` 한 줄 "체험 대화를 모두 썼어요. 이제부터는 매달 5회를 쓸 수 있어요."를 보여 주고, 이용량 표시가 "이번 달 n/5"로 바뀐다(PRD `F10-R07`). 응답의 `usage.chat.pool`이 `trial`에서 `month`로 바뀐 것을 보고 앱이 띄운다. 대화 기록에 저장하지 않으므로 다시 열면 보이지 않는다. 숫자는 한도 설정값에서 가져온다.

한도 안내 카드: 제목 "이번 달 AI 대화를 모두 썼어요", 다음 초기화 날짜, "캘린더와 기록은 계속 쓸 수 있어요", 주 버튼 [Pro 알아보기]. 위협하거나 재촉하는 문구를 쓰지 않는다.

## 8. 훈련 종류, 상태, 아이콘

### 8.1 훈련 종류

색만으로 구분하지 않고 항상 종류 이름을 함께 쓴다. 색은 점, 달력 표시, 칩의 테두리처럼 작은 면적에만 쓴다.

| `type` | 표시 이름 | 토큰 | 다크 | 라이트 | 체감 안내 문구 |
|---|---|---|---|---|---|
| `walk_run` | 걷고 달리기 | `session.walkRun` | `#3CC8C8` | `#0E8F8F` | 걷기와 달리기를 번갈아 해요 |
| `easy` | 가볍게 달리기 | `session.easy` | `#6AA6FF` | `#1E6FE0` | 편하게 대화할 수 있는 속도예요 |
| `tempo` | 조금 빠르게 달리기 | `session.tempo` | `#B8E04A` | `#567300` | 숨이 조금 차지만 유지할 수 있는 속도예요 |
| `long` | 길게 달리기 | `session.long` | `#A98BFF` | `#6B3FE0` | 편한 속도로 평소보다 오래 달려요 |
| `race` | 대회 | `session.race` | `#FF6FC4` | `#D63A9E` | 대회 날이에요 |

표시 이름과 문구는 `packages/shared`에 둔다(API_SPEC §2.2). `long`의 이름은 '길게 달리기'다(`UX-10`, C2 시안에서 통일).

- `tempo`의 이전 Figma 값(다크 `#FF9F4A`, 라이트 `#D9620A`)은 주황이라 포인트 색과 구분되지 않는다(대비 1.53:1, 1.01:1). 주황은 '오늘' 표시에도 쓰므로 헷갈린다.
- 새 색은 연두(`#B8E04A`, 라이트 `#567300`)다(`UX-08`, 2026-11-18 확정, Figma 반영). 다른 색이 차지하지 않은 색상 범위가 노랑(`warning`)과 초록(`success`) 사이뿐이라 그 가운데에 두었다. 색상각은 76°로 `warning`(36°)과 40°, `success`(151°)와 75° 떨어진다. 대비는 다크 카드 위 11.26:1, 라이트 바탕 위 5.00:1이다. 훈련 종류는 항상 이름과 함께 쓰고(§8.1), 상태는 칩 글자로 쓰므로(§8.2) 색만으로 헷갈리지는 않는다.
- 다른 종류의 색도 바탕이 남색으로 바뀌었으므로, Figma 값과 맞추고 3:1을 다시 확인한다. 위 표의 값은 다크는 카드 위에서 모두 6:1 이상, 라이트는 바탕·카드·패널 위에서 모두 3:1 이상이다(라이트 `tempo`가 가장 낮은 3.28:1).

### 8.2 훈련 상태

| `status` | 칩 문구 | 색 | 아이콘 |
|---|---|---|---|
| `planned` | 예정 | `text.secondary` | 없음 |
| `completed` | 완료 | `text.success` | 체크 |
| `missed` | 미완료 | `text.warning` | 빈 원 |
| `skipped` | 생략 | `text.disabled` | 없음 |

미완료에 오류 색(빨강)을 쓰지 않는다. 훈련을 놓친 것은 잘못이 아니다.

### 8.3 아이콘

아이콘은 의미 이름으로 부르고, 실제 아이콘과의 대응은 파일 하나에 둔다. 아이콘은 직접 그린 선 아이콘만 쓴다(`UX-04`). 선 굵기와 끝 모양은 Figma의 아이콘과 같게 한다. 이모지를 아이콘 대신 쓰지 않는다.

필요한 의미 이름: `home`, `coach`, `calendar`, `record`, `profile`, `run`, `walk`, `flag`, `check`, `close`, `back`, `next`, `add`, `edit`, `delete`, `send`, `swap`, `warning`, `info`, `bell`, `crown`, `chevron`, `more`.

Figma의 `C2/Icon`은 위 23개를 모두 갖췄다(2026-11-18). 빠져 있던 `walk`, `edit`, `delete`, `warning`, `info`, `crown`, `chevron`, `more`는 새로 그렸다. 이름이 다른 것은 아래와 같고, 코드에서는 위의 의미 이름을 쓴다.

| 의미 이름 | Figma 아이콘 |
|---|---|
| `next` | 오른쪽 꺾쇠 |
| `chevron` | 아래쪽 꺾쇠 |
| `send` | `up` |
| `profile` | `my` |

## 9. 문구

### 9.1 어조

| 원칙 | 예 |
|---|---|
| 해요체 존댓말 | "일정을 변경했어요" (○) / "변경되었습니다" (×) |
| 짧게, 한 문장에 한 가지 | "이 제안은 만료됐어요. 다시 물어봐 주세요." |
| 할 수 있는 일을 알려 준다 | "인터넷 연결을 확인하고 다시 시도해 주세요." |
| 탓하지 않는다 | "어제 훈련을 놓쳤어요. 이번 주 일정을 다시 짤까요?" (○) / "훈련을 하지 않았습니다" (×) |
| 실패를 숨기지 않는다 | "변경하지 못했어요." (○) / 실패했는데 아무 표시 없음 (×) |
| 버튼은 동작을 말한다 | "적용하기", "기록 저장" (○) / "확인", "예" (×) |
| 의료 표현을 쓰지 않는다 | "통증이 계속되면 진료를 받아 보세요" (○) / "염좌로 보여요" (×) |
| 이모지를 쓰지 않는다 | 화면 문구, 버튼, 시스템 메시지, 카드에는 이모지를 쓰지 않는다. 필요한 곳에는 선 아이콘(§8.3)을 쓴다 |

화면 문구는 어느 코치를 골라도 같다. 코치의 말투는 AI 코치의 응답에만 쓴다(PRD `AI-11`). 알림 문구에 코치 말투를 쓸지는 정하지 않았고(PRD `D-16`), 정할 때까지 위의 중립 어조를 쓴다.

### 9.2 용어

전문 용어는 화면에 쓰지 않는다. 훈련 상세의 보조 설명에만 괄호로 덧붙일 수 있다(`F03-R07`).

| 워크 런 | 걷고 달리기 |

| 컨디션 | MVP에서 받지 않는다 |
