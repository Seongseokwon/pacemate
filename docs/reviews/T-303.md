# T-303 교차 검토 (Claude Code)

대상: PR #57이 병합된 `b027de2`의 HealthKit 가져오기(`apps/mobile/src/health/healthkit.ts`, `records.tsx`, `services/api/src/workout/workout.service.ts`의 `importHealthkit`, 마이그레이션 두 개, `packages/shared`의 스키마). 기준은 `URGENT_PRE_MVP.md` §1의 완료 기준, PRD `F07-R03`~`R06`, `F07-R11`, `DI-10`, 인수 기준 `AC-F07-01`~`04`다. 이 검토는 코드를 수정하지 않았다. 검토 시점(2026-11-19)에 `pnpm check`는 통과했다(API 246, 앱 179, Training Engine 104, shared 34).

## 수정이 필요한 사항

1. **중복 판단이 "완전히 같은 값"만 본다. 실제 중복은 대부분 빠져나간다** (`F07-R11`, `URGENT_PRE_MVP.md` §1 "중복 제거").
   - 서버는 같은 사용자의 HealthKit ID 또는 `date`, `distance_km`(0.01km), `duration_sec`(1초)가 모두 같을 때만 중복으로 본다. 문서에 적힌 대로 구현했다. 하지만 실제로 겹치는 경우는 값이 조금씩 다르다.
     - 수동 기록은 보통 반올림해서 적는다(5km, 30분). Apple 건강 값은 5.03km, 30분 12초다. 이러면 둘 다 저장된다.
     - 같은 달리기를 Apple Watch와 iPhone 앱(또는 다른 러닝 앱)이 함께 기록하면 HealthKit에 UUID가 다른 운동이 두 개 생기고 값도 조금 다르다. 이것도 둘 다 저장된다.
   - 결과: 같은 달리기가 두 번 쌓인다. 이번 주·이번 달 거리와 횟수가 부풀고, 이게 화면 통계에서 끝나지 않는다. 최근 주간 거리를 쓰는 곳(`proposal.service.ts`의 `recentWeeklyKmOf`: 목표 변경, `plan.service.ts`: 유지 계획의 최근 기록)이 실제보다 많이 달린 것으로 보고 훈련량을 잡는다. 안전 규칙의 기준값이 올라가는 셈이다. 채팅 도구 `get_workout_history`도 같은 달리기를 두 번 보여 준다.
   - 수동 기록이 같은 날 훈련에 이미 연결된 경우, 가져온 기록은 연결할 훈련이 없어 "자유 러닝"으로 따로 저장된다. 그래서 목록에서도 중복인지 알아보기 어렵다.
   - PRD 문구("같은 날짜·거리·시간")를 바꾸는 일이라 개발자 결정이 필요하다. 선택지 예:
     - (권장) 같은 날짜에 이미 기록이 있고 거리 차이가 ±5%(또는 0.2km) 안, 시간 차이가 ±2분 안이면 중복으로 본다. 허용 오차는 (초기값) 상수로 둔다.
     - 같은 날짜에 기록이 이미 있으면 저장하지 않고 건너뛴 개수만 알려 준다. 사용자가 직접 정리한다.
     - HealthKit 쪽 중복(시계와 휴대폰)은 시작 시각이 겹치는지로도 거를 수 있다. 다만 요청에 시작·종료 시각을 더해야 한다.
   - 지금 테스트는 정확히 같은 값만 확인한다(`workout.e2e.test.ts`의 "수동 기록과 중복을 제거"). 조금 다른 값으로 확인하는 사례를 더해야 한다.

## 확인이 필요한 사항

2. **같은 날 달리기가 둘이면 어느 쪽이 훈련에 연결될지 정해져 있지 않다** (`F07-R04`). 앱은 `queryWorkoutSamples`를 `ascending` 없이 부르고 받은 순서대로 한 건씩 보낸다. 서버는 먼저 도착한 기록을 그날 훈련에 연결한다. 그래서 몸풀기 2km와 본 훈련 10km가 같은 날이면 라이브러리 기본 순서에 따라 2km가 연결될 수 있다. 개발자가 정할 선택지는 둘이다. 하나는 거리가 훈련 거리에 가장 가까운 기록을 연결하는 것이고, 다른 하나는 오래된 순서(`ascending: true`)로 보내고 그 한계를 문서에 적는 것이다. 사용자는 기록 수정에서 연결을 바꿀 수 있으므로 1번보다 급하지 않다.

3. **수동 기록의 연결 규칙과 다르다** (`F07-R04`). 수동 기록은 연결을 "제안"하고 사용자가 고른다. 가져온 기록은 묻지 않고 바로 연결한다. `URGENT_PRE_MVP.md`가 "자동 연결"을 요구하므로 의도한 동작으로 보이지만, PRD `F07-R04`와 `F07-R11`에는 이 차이가 적혀 있지 않다. `F07-R11`에 "같은 날짜의 연결 가능한 훈련에 자동으로 연결한다"를 적어 두는 편이 낫다.

4. **쓰기 권한 문구** (`app.json`). 이 앱은 쓰기 권한을 요청하지 않는데 `NSHealthUpdateUsageDescription`이 "건강 데이터를 업데이트하지 않습니다."로 들어가 있다. 설정 플러그인 때문에 값이 필요하다면 그대로 둬도 되지만, 심사에서 목적 문구를 지적받을 수 있다. `T-504`(스토어 제출)에서 다시 확인한다.

## 나머지 확인 결과

- 권한과 범위: 운동, 걷기·달리기 거리, 심박수만 읽기로 요청한다. 쓰기는 요청하지 않는다. 최근 30일의 달리기만 조회한다. 읽기 권한 거부는 HealthKit이 알려 주지 않는다. 그래서 결과가 0건이면 권한을 확인하라는 문구를 보여 준다. 기기에서 확인할 부분은 B-21로 남아 있다.
- Android: 버튼이 iOS에서만 보인다. 라이브러리 16.2.0은 iOS가 아닌 플랫폼에서 `src/healthkit.ts` 대체 구현을 쓰고, `isHealthDataAvailable`이 `false`를 돌려준다. 그래서 Android에서 가져오기 모듈을 불러와도 앱이 죽지 않는다.
- 단위: `totalDistance`는 라이브러리가 미터로 돌려주므로 1000으로 나누는 것이 맞다. 거리 통계를 우선하고 없으면 `totalDistance`를 쓴다.
- 날짜: 시작 시각을 `Asia/Seoul` 날짜로 바꾼다. 서버의 `today()`와 기준이 같다. 미래 날짜는 서버가 400으로 거절한다.
- 동시성과 정합성: 사용자 행을 잠근 뒤 HealthKit ID를 확인하고 기록한다. 연결할 훈련은 계획을 잠근 뒤 다시 읽는다. 동시에 두 번 보내도 한 건만 저장되는 것을 실제 PostgreSQL 테스트로 확인했다. `planned_session_id` 유일 제약과 연결 조건(생략하지 않은 훈련, 활성 계획, 연결된 기록 없음)이 함께 있어 `DI-10`, `AC-F07-04`가 지켜진다.
- 구조 규칙: `planned_sessions`를 고치지 않고 `workout_logs.planned_session_id`만 설정한다(`DI-01`). 새 테이블 `healthkit_imports`에는 행 수준 보안이 켜져 있고 정책은 없다. 사용자 ID는 토큰에서 얻는다. 채팅 제안의 `workout` 내용 스키마에 `averageHeartRate`가 선택 필드로 추가됐지만, 제안 내용은 서버가 만들기 때문에 LLM이 심박수를 저장할 경로는 없다.
- 출처 표시: 목록에 "· Apple 건강", 상세에 "Apple 건강에서 가져옴"과 평균 심박수가 표시된다. 다만 `records.test.tsx`는 가져오기 모듈을 모의로 바꿨을 뿐이고, 버튼·결과 문구·출처 표시를 확인하는 화면 테스트는 없다. 가져오기 변환 로직은 `healthkit.test.ts`가 확인한다.
- 실패 표시(`F05-R07`): 일부만 실패하면 실패한 개수를 따로 알린다. 로그인·동의 이동이 필요한 오류는 바로 넘긴다. 실패를 성공처럼 표시하지 않는다.
- 인수 기준: `AC-F07-01`(가져온 기록이 연결되면 훈련 완료), `AC-F07-02`(삭제하면 연결 해제), `AC-F07-03`(페이스 계산), `AC-F07-04`(1:1 연결)는 가져온 기록에도 그대로 맞는다.

판정: 1번은 사용자가 수동 입력과 가져오기를 함께 쓰면 거의 반드시 생기고, 훈련량 기준값까지 바꾼다. 출시 전에 개발자가 중복 기준을 정한 뒤 보완해야 한다. 2~4번은 문서를 보완하거나 기기 확인(B-21) 때 함께 보면 된다.

## 개발자 결정 (2026-11-19)

`DECISIONS.md` 2026-11-19 "기록과 훈련의 연결, Apple 건강 중복 기록"에 적었다. 요약:

- 1번(중복): 중복으로 보이는 기록도 지우지 않고 모두 저장한다. 비슷한 기록(Apple 건강끼리는 시각이 겹침, 수동 기록과는 거리 ±5%·시간 ±2분)을 묶어 사용자가 나란히 비교할 수 있게 한다.
- 2번(같은 날 여러 기록): 같은 날 기록이 셋 이상일 수 있다. 연결할 기록은 사용자가 고른다. 이미 연결된 훈련을 고르면 기존 연결을 자동으로 풀고 새 기록에 연결한다. 나눠 달린 기록의 합산은 출시 뒤 검토한다.
- 3번: 이 결정에 맞춰 PRD `F07-R04`, `F07-R11`을 고친다.
- 4번: 거리 없는 기록은 건너뛰고 개수를 따로 알린다. 쓰기 권한 문구는 `T-504`에서 본다.

- 비슷한 기록을 모두 저장하면 같은 달리기가 통계와 최근 주간 거리(목표 변경, 유지 계획의 기준값)에 여러 번 들어간다. 집계에서 어떻게 셀지
