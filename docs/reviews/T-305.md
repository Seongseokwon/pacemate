# T-305 교차 검토 (Claude Code)

대상: PR #66이 병합된 `76c0cac`의 기록 연결과 비슷한 기록 묶기(`services/api/src/workout/workout.service.ts`, `services/api/src/workout/similar.ts`, 마이그레이션 `20261120000000_workout_similarity`, `packages/shared`의 스키마, `apps/mobile/src/app/(tabs)/records.tsx`, `apps/mobile/src/health/healthkit.ts`, `plan.service.ts`·`proposal.service.ts`의 최근 기록 집계). 기준은 `DEVELOPMENT_PLAN.md`의 `T-305` 완료 조건, PRD `F07-R04`, `F07-R05`, `F07-R11`, `DI-10`, 인수 기준 `AC-F07-01`~`04`, `DECISIONS.md` 2026-11-19다. 이 검토는 제품 코드를 고치지 않았다. 검토 시점(2026-11-20)에 `pnpm check`는 통과했다(API 279, 앱 223, Training Engine 104, shared 34). 아래 1·2번은 임시 e2e 테스트로 재현한 뒤 그 테스트를 지웠다.

## 수정이 필요한 사항

1. **자동 연결된 Apple 건강 기록의 날짜를 바꾸면, 그 뒤 원래 날짜의 가져오기가 계속 실패한다** (`F07-R11`, `F05-R07`).
   - 재현: 11-17의 5km 훈련에 Apple 건강 기록이 자동 연결된다 → 사용자가 기록 수정에서 날짜만 11-16으로 바꾼다(`PATCH { date }`, 200) → 11-17의 다른 Apple 건강 기록을 가져온다 → `500 INTERNAL_ERROR`. 같은 기록을 다시 보내도 500이다.
   - 원인: `PATCH`가 `plannedSessionId`를 건드리지 않으면 `autoLinked`가 `true`로 남는다. 그래서 11-17 훈련이 11-16 기록에 자동 연결된 상태가 된다. `importHealthkit`은 `available`에 "자동 연결된 기록이 붙은 훈련"을 넣지만, 연결을 풀 대상(`records`)은 같은 날 기록만 본다. 다른 날 기록의 연결은 풀리지 않은 채 새 기록을 그 훈련에 연결하려다 `planned_session_id` 유일 제약에 걸린다. `P2002`를 잡지 않아 500이 된다.
   - 영향: 트랜잭션이 통째로 되돌려져 `healthkit_imports` 표시도 남지 않는다. 그래서 그날의 Apple 건강 기록은 가져올 때마다 "n개를 가져오지 못했어요"가 된다. 사용자가 날짜를 바로잡기 전까지 풀리지 않는다.
   - 고치는 방법 예: `available`을 "연결된 기록이 없거나, 연결된 기록이 `records`에 들어 있는 훈련"으로 좁힌다. 또는 `PATCH`에서 날짜가 바뀌면 `autoLinked`를 `false`로 내린다. 둘 다 하는 편이 안전하다. 재현 사례를 `workout.e2e.test.ts`에 더한다.

2. **채팅의 주간 요약 거리가 비슷한 기록을 두 번 센다** (`F07-R11`의 "통계에는 묶음당 하나만", `DECISIONS.md` 2026-11-19).
   - 재현: 같은 날 수동 5km(30분)와 Apple 건강 5.03km(30분 12초)를 저장한다 → `GET /v1/workouts/stats`의 이번 주는 `5.03km, 1회`로 맞다. 하지만 `SummaryService.weeklyNumbers`의 `totalDistanceKm`은 `10.03`이다.
   - 원인: `summary.service.ts`가 아직 `workoutLog.aggregate`로 모든 기록의 거리를 더한다. `T-305`는 기록 통계, 유지 계획, 목표 변경의 최근 주간 거리만 `representativeWorkouts`로 바꿨다.
   - 영향: 채팅의 주간 요약 카드(`chat.service.ts`의 `weekly_summary`)와 도구 `get_weekly_summary`가 부풀린 거리를 보여 준다. 기록 탭의 이번 주 거리와도 숫자가 달라진다. 나중에 `T-602`(주간 요약)도 이 함수를 쓴다.
   - 고치는 방법: 주간 요약 거리도 `representativeWorkouts`로 센다. 테스트를 더한다.
   - 같은 맥락: 도구 `get_workout_history`는 비슷한 기록을 따로따로, 묶음 표시 없이 돌려준다. 그래서 LLM이 거리를 더하면 같은 달리기를 두 번 셀 수 있다. 묶음 정보(예: 대표 기록 여부)를 붙일지 정해야 한다. API_SPEC §6를 먼저 고쳐야 하는 일이라 2번과 따로 판단해도 된다.

## 확인이 필요한 사항

3. **사용자가 훈련을 다른 기록으로 옮기면, 밀려난 기록은 자동 연결에서 영구히 빠진다** (`F07-R04`). `save`가 기존 기록의 연결을 풀 때 `manualLink: true`로 표시한다. 그래서 밀려난 기록이 Apple 건강 기록이면, 사용자가 나중에 새 연결을 풀어도 다음 가져오기에서 다시 연결되지 않는다. 사용자가 그 기록을 직접 고르지는 않았으므로, `manualLink`는 그대로 두고 `autoLinked`만 내리는 편이 의도에 가까워 보인다. 개발자 판단이 필요하다.

4. **채팅으로 기록할 때는 연결 규칙이 다르다** (`F07-R04`, `F07-R07`). 화면에서는 이미 연결된 훈련을 고르면 기존 연결을 풀지만, 채팅의 기록 제안(`proposal.service.ts`)은 여전히 `SESSION_ALREADY_COMPLETED`로 거절한다. 채팅으로 기록하는 경우 그 훈련에는 대개 같은 달리기의 Apple 건강 기록이 이미 붙어 있으므로 지금 동작도 무리는 없다. 다만 PRD `F07-R04`가 "기록 저장·수정 시"로 넓게 적혀 있으니, 채팅은 예외라는 점을 `F07-R07` 또는 §6.5에 적어 두는 편이 낫다.

5. **이미 있던 기록은 자동 연결이 굳는다.** 마이그레이션이 `auto_linked`를 `false`로 채우므로, `T-305` 전에 자동 연결된 Apple 건강 기록은 사용자가 고른 연결처럼 다뤄져 다시 짝지어지지 않는다. 시작·종료 시각이 없는 기존 Apple 건강 기록끼리 묶이지 않는다는 점은 DATABASE에 적혀 있다. 아직 운영 데이터가 없으므로 문서에 한 줄 적는 것으로 충분하다.

6. **화면** (`records.tsx`).
   - [다른 달리기예요]는 되돌릴 방법이 없다. API는 `separateRun: false`를 받지만 화면에 버튼이 없다. 잘못 누르면 집계가 계속 두 번 들어간다. 확인 창을 띄우거나 되돌리기를 두는 편이 낫다.
   - 비슷한 기록이 둘 이상이면 하나를 누를 때 모든 [다른 달리기예요] 버튼이 함께 로딩으로 바뀐다(`separate.isPending`을 같이 씀).
   - 분리 실패 문구가 삭제 오류 상태(`deleteError`)를 같이 쓴다. 지금은 동작하지만 이름과 쓰임이 다르다.
   - 이미 연결된 훈련을 고를 때 "· 다른 기록과 연결됨"만 보이고, 저장하면 기존 연결이 풀린다는 안내는 없다. 이 선택과 기본값(같은 날 비어 있는 훈련만 자동 선택)을 확인하는 화면 테스트도 없다.

## 나머지 확인 결과

- 완료 조건 대조:
  - "같은 날 기록이 셋 이상이어도 사용자가 고른 기록이 연결된다": e2e "같은 날 기록이 셋 이상이면…"이 확인한다. 통과.
  - "10km 훈련과 2km·10km 기록을 어느 순서로 가져와도 10km 기록이 연결된다": 두 순서 모두 e2e가 있다. 가져올 때마다 같은 날 자동 연결 대상 전체를 다시 짝지으므로, 사용자가 고른 연결이 끼지 않으면 순서와 상관없이 결과가 같다. 통과.
  - "비슷한 기록이 모두 남고 집계에는 하나만 들어간다": 기록 통계, 유지 계획, 목표 변경은 맞다. 주간 요약은 2번 때문에 미충족.
  - "동시 연결 변경을 실제 DB로 검증한다": e2e "동시에 연결을 바꿔도…"가 실제 PostgreSQL로 확인한다. 통과.
  - "거리 없는 기록 개수 알림": `healthkit.ts`가 따로 세고 화면 문구에 넣는다. 단위 테스트가 있다. 통과.
- 동시성: 기록 저장·수정, Apple 건강 가져오기, 제안 승인이 모두 사용자 행을 먼저 잠그고 그다음 계획을 잠근다. 잠금 순서가 같아 교착 위험이 없다. 유일 제약(`planned_session_id`)이 1:1 연결(`DI-10`, `AC-F07-04`)을 끝까지 보장한다.
- 짝짓기: 거리 차이가 작은 짝부터 차례로 고른다(탐욕 방식). PRD 문구("거리 차이가 가장 작은 짝끼리")와 맞다. 동률은 훈련 ID, HealthKit ID 순으로 정해 결과가 일정하다. 시간 기반 훈련은 거리 기반 훈련 다음에 시간 차이로 짝짓는다.
- 묶기(`similar.ts`): Apple 건강끼리는 시각이 겹칠 때, 수동·채팅 기록과는 같은 날 거리 ±5%·시간 ±2분일 때 묶는다. 수동 기록끼리는 묶지 않는다(같은 값은 기존 `WORKOUT_DUPLICATE` 확인이 막는다). 묶음은 이어진 것끼리 합친다. 대표 기록은 연결된 기록 → 긴 기록 → ID 순이다. PRD `F07-R11`과 맞다. 허용 오차 두 값은 (초기값)인데 `similar.ts` 안의 상수다. 설정 상수 한 곳에 두라는 코드 규칙에 따라 `WORKOUT_LIMITS` 옆(`packages/shared/src/config.ts`)으로 옮기는 편이 낫다.
- 구조 규칙: `planned_sessions`를 고치지 않고 `workout_logs.planned_session_id`만 바꾼다(`DI-01`). 새 열만 추가해 행 수준 보안은 그대로다. 사용자 ID는 토큰에서 얻고 모든 조회에 `userId` 조건이 있다(`GET /v1/workouts/{id}/similar` 포함). LLM 경로에는 바뀐 것이 없다.
- 문서: PRD `F07-R04`, `F07-R11`, API_SPEC §3.4, DATABASE §3.5, DEVELOPMENT_PLAN §7(B-21 갱신, B-25 추가)가 구현과 맞다. 다른 문서가 인용하는 요구사항 ID는 바뀌지 않았다.
- 기기 확인: B-25와 `apps/mobile/maestro/b25-similar-workouts.yaml`이 있다. 로그인(`T-106`) 뒤에 돌릴 수 있다.

판정: 1번은 사용자가 기록 날짜를 고치는 흔한 동작으로 가져오기가 계속 막히고 500이 난다. 2번은 결정한 집계 규칙이 채팅 요약에서 빠져 같은 주에 숫자가 두 개가 된다. 둘 다 출시 전에 고쳐야 하며 범위가 작다. 3~6번은 개발자 판단이나 작은 보완이고, 기기 확인(B-25) 때 함께 보면 된다.
