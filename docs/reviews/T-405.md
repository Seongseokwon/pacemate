# T-405 교차 검토 (Codex)

대상: main `05d2a135`의 도구 레지스트리와 조회 4개·제안 3개. 기준: PRD §11, §6.1~6.3과 API_SPEC §6. 코드 변경 없이 정적으로 검토했다. 아래 테스트는 기존 테스트의 내용이며 이번 검토에서 통과한 것으로 판정하지 않는다.

## 수정 또는 확인이 필요한 사항

- **새 제안 생성 후 채팅이 실패하면 기존 제안이 사라질 수 있다** (`DI-05`, `AC-F05-02`, `AC-F04-06`). 제안 생성은 기존 대기 제안을 즉시 `superseded`로 바꾸고 새 제안을 저장한다(`proposal.service.ts`의 `insert`). 이후 LLM 호출 또는 응답 저장이 실패하면 채팅 처리기는 이번에 만든 새 제안만 취소한다(`chat.service.ts`의 `fail`). 이전 제안은 복구되지 않아 사용자가 새 카드를 받지 못한 채 기존 카드도 사용할 수 없게 된다. 실제 훈련은 변경되지 않지만, 실패한 요청이 기존 대기 제안의 사용 가능 상태를 바꾼다. 실패 시 기존 제안을 유지해야 하는지 결정하고 동시 요청을 포함해 검증할 필요가 있다.

## 인수 기준별 결과

- `AC-F04-01`, `AC-F04-02`: 조회 도구는 실제 계획·기록 서비스와 DB를 사용하고, 제안 도구는 서버 제안 서비스에 위임한다. `chat-tools.e2e.test.ts`는 7개 도구의 정상·입력 오류를 다룬다. 실제 모델의 도구 선택과 답변 정확도는 T-407 평가 전이라 미확인이다.
- `AC-F05-02`, `AC-F07-05`: 도구는 제안만 생성하고 승인 전 일정과 기록을 직접 바꾸지 않는다. 관련 테스트가 있다. 위의 기존 제안 대체 문제는 별도로 남는다.
- `AC-F05-06`, `AC-F05-09`, `AC-F05-10`: 도구는 제안 서비스와 Training Engine에 변경 검증을 위임한다. 대상 범위와 실패 사유를 반환하는 테스트가 있다. 승인 후 전체 안전성은 제안 모듈 검증 범위다.
- `AC-F02-06`: 기록 부족 시 `RECENT_DISTANCE_REQUIRED`와 사용자 응답으로 전달한 주간 거리를 처리하는 테스트가 있다. 실제 모델이 질문을 적절히 하는지는 T-407에서 확인해야 한다.
- 사용자 식별은 도구 인자가 아닌 서버 컨텍스트에서 전달하며, 훈련 수치는 제안 도구 입력에 없다. `condition`도 기록 제안 입력에 없다.

판정: 도구 계약의 주요 경로와 기존 테스트는 확인했으나, 위 실패 시 기존 제안 상태와 실제 모델의 도구 사용은 추가 확인이 필요하다.
